# ระบบหลังบ้านของ SWINE SYNC — เอกสารออกแบบ

> **สถานะ: ออกแบบ ยังไม่ได้ลงมือ** · ตัดสินใจแล้วค่อยเปิดงานใน `TASKS.md`
> คู่กับ `DATABASE.md` (โครงตาราง) — อ่านสองไฟล์นี้ประกอบกัน

ออกแบบจากข้อมูลที่หน้าจอ **ใช้อยู่จริง** ใน `src/data/mock/` และ `src/lib/` ทุกอย่างในนี้
มีหน้าใดหน้าหนึ่งรออยู่แล้ว ไม่ได้เผื่ออนาคตลอย ๆ

**ตัวเลือกที่ตกลงกันไว้แล้ว** (ถามยืนยันกับผู้ใช้ทีละข้อ)

| เรื่อง | ที่เลือก |
|---|---|
| สแตก | Node + Express + **PostgreSQL** (พิจารณา MongoDB แล้ว — เหตุผลที่ไม่เอาอยู่ในข้อ 2) |
| รันที่ไหน | **เซิร์ฟเวอร์ของตัวเอง ไม่ใช่คลาวด์** · ทุกส่วนขึ้น **Docker** (ดูข้อ 13) |
| ผู้ใช้ | สร้างในระบบเอง ไม่ต้องต่อ AD/SSO |
| สิทธิ์ | 2 ระดับพอ (admin / user) ค่อยเพิ่มระดับกลางทีหลัง |
| ค่าเซนเซอร์ | ยังไม่มีอุปกรณ์จริง — เขียนตัวจำลองไปก่อน |
| ภาพจากกล้อง | MinIO (พูดภาษา S3) เป็นอีก service ใน compose |
| เก็บย้อนหลัง | **ยังไม่กำหนด** — ออกแบบให้เป็นค่าตั้งที่แก้ได้ ไม่ฝังในโค้ด (ดูข้อ 14) |
| ขอบเขตรอบแรก | แกนก่อน (ผู้ใช้+สิทธิ์ · ฟาร์ม/โรงเรือน/อุปกรณ์ · เซนเซอร์+ชั้นสรุป · แจ้งเตือน · ค่าตั้งของผู้ใช้) |
| ส่งมอบ | เอกสารออกแบบ แล้วค่อยตัดสินว่าจะทำต่อ |

## 1. ปัญหาที่ backend มาแก้ (ไม่ใช่ "มีเพราะควรมี")

หน้าบ้านตอนนี้เก็บทุกอย่างใน localStorage ของแต่ละเครื่อง ซึ่งทำให้เกิดสามเรื่องที่แก้ในหน้าจอไม่ได้:

1. **สองคนเปิดหน้าเดียวกันเห็นคนละเลข** — เกณฑ์อุณหภูมิ/ความชื้นอยู่ใน `swine-sync:settings`
   ของแต่ละเครื่อง แล้วแจ้งเตือนถูก *คำนวณใหม่ทุกครั้งที่ render* จากเกณฑ์ชุดนั้น
   ผู้จัดการตั้ง 28 °C คนหน้าฟาร์มตั้ง 30 °C → คุยกันคนละเรื่องทั้งที่ดูจอเดียวกัน
2. **งานที่บันทึกไปหายเมื่อล้างเบราว์เซอร์** — หมูตาย/ป่วย · ปรับจำนวนสุกร · ภาพจากกล้อง
   ทั้งหมดอยู่ในเครื่องคนบันทึก คนอื่นไม่เห็น และไม่มีประวัติว่าใครทำอะไร
3. **สิทธิ์เป็นแค่การแบ่งหน้าที่ ไม่ใช่การกัน** — `lib/auth/accounts.js` ตรวจรหัสผ่านในเบราว์เซอร์
   ใครแก้ไฟล์ในเครื่องตัวเองก็เป็นแอดมินได้ (ตอนนี้กันได้แค่ระดับ "อย่าเผลอ")

ทั้งสามข้อมีทางแก้เดียวคือย้ายไปอยู่ฝั่งเซิร์ฟเวอร์ นี่คือเหตุผลของทั้งเอกสาร

## 2. สแตกและเหตุผลที่เลือก

```
PostgreSQL 16 + TimescaleDB       ← ฐานเดียว ไม่แยก
Node 22 + Express 5               ← ภาษาเดียวกับหน้าบ้าน
node-postgres (pg) + SQL ตรง ๆ    ← ไม่ใช้ ORM หนัก
node-pg-migrate                   ← migration เป็นไฟล์ ไล่ย้อนได้
argon2id                          ← แฮชรหัสผ่าน
zod                               ← ตรวจ input ทุกเส้นทาง
pino                              ← log แบบ JSON
vitest + supertest                ← เทสต์
```

**ทำไม Postgres ไม่ใช่ MongoDB** — ข้อมูลชุดนี้เป็นตารางล้วนและมีความสัมพันธ์แน่น
(ฟาร์ม → โรงเรือน → อุปกรณ์ → ค่าที่วัดได้) คำถามที่หน้าจอถามคือ "ค่าเฉลี่ยรายชั่วโมง
ของโรงเรือนนี้ 24 ชม." ซึ่งเป็น `GROUP BY` ตรง ๆ ไม่ใช่การอ่านเอกสารทีละใบ

**ทำไม TimescaleDB** — ตัวเลขตัดสินคือ **~200 ล้านแถว/ปี** (คำนวณในข้อ 4 ของ `DATABASE.md`)
Timescale เป็น extension ของ Postgres ตัวเดียวกัน ไม่ใช่ฐานใหม่ ได้มา 3 อย่างที่เขียนเองแล้วเจ็บ:
แบ่ง partition ตามเวลาอัตโนมัติ · บีบอัดข้อมูลเก่า (~10 เท่า) · continuous aggregate ที่อัปเดตเองไม่ต้องตั้ง cron
**ถ้าติดตั้ง extension ไม่ได้** (บาง managed service ไม่ให้) — ใช้ Postgres ล้วนแล้ว
`PARTITION BY RANGE (at)` รายเดือน + ตารางสรุปที่ refresh ด้วย cron แทน เสียแรงเพิ่มแต่ไม่ตัน

**ทำไมไม่ใช้ MongoDB** (ถามมาแล้วและพิจารณาจริงจัง ไม่ได้ปัดตก)
เรื่องเซนเซอร์ MongoDB สู้ได้ — Time Series Collection บีบอัดดีและรับ 200 ล้านแถว/ปีไหว
**จุดที่แพ้คือคำถามที่หน้าจอถามจริง ๆ ซึ่งเป็นการ join แทบทั้งหมด**
"ฟาร์มนี้มีสุกรกี่ตัว" = รวมทุกโรงเรือน + บวกยอดที่คนปรับเอง ·
"หลุดเกณฑ์กี่หลัง" = ค่าล่าสุดทุกโรงเรือนเทียบเกณฑ์ที่แอดมินตั้ง
ใน Postgres เป็น view ใบเดียวที่ทุกหน้าเรียกร่วมกัน (ข้อ 8 ของ `DATABASE.md`)
ใน Mongo ต้อง `$lookup` ซึ่งช้า หรือ denormalize เก็บซ้ำหลายที่ —
**ซึ่งคือต้นเหตุของบั๊ก T1.65 เป๊ะ ๆ ที่โปรเจกต์นี้เคยเจอ** (หน้าภาพรวมบอก "หลุดเกณฑ์ 17 หลัง"
แต่หน้าอุณหภูมิบอก 30 เพราะคำนวณคนละที่)
บวกกับชั้นสรุปที่ Timescale อัปเดตให้เอง แต่ฝั่ง Mongo ต้องเขียน job รวมยอดเองพร้อมจัดการ
ข้อมูลมาช้า/ส่งซ้ำ — เพิ่มงานจริงราว 1–2 สัปดาห์โดยไม่ได้อะไรกลับมา
(Docker ไม่ใช่เหตุผลให้เลือกฝั่งไหน ทั้งคู่มี official image เหมือนกัน)

**ทำไมไม่ใช้ ORM (Prisma/TypeORM)** — งานหนักของระบบนี้คือ time-series aggregate กับ window function
ซึ่ง ORM เขียนออกมาแล้วอ่านไม่รู้เรื่องและ tune ไม่ได้ ใช้ `pg` + SQL ในไฟล์แยกจะตรงกว่า
(ยังคง type ได้ด้วย zod ที่ขอบ) ORM คุ้มตอนมี CRUD 50 ตารางที่หน้าตาเหมือนกัน ซึ่งไม่ใช่กรณีนี้

## 3. โครงโปรเจกต์

วางเป็น **repo เดียวสองโฟลเดอร์** ไม่แยก repo — เพราะสัญญาข้อมูลระหว่างหน้าบ้าน/หลังบ้าน
ยังขยับบ่อย อยู่ด้วยกันแล้วแก้พร้อมกันใน commit เดียวได้

```
cpf_dashboard/
  src/                    ← หน้าบ้านเดิม ไม่ย้าย
  server/
    src/
      app.js              สร้าง Express app (แยกจาก listen เพื่อให้เทสต์เรียกได้)
      index.js            เปิดพอร์ต + ปิดให้เรียบร้อยตอนโดน SIGTERM
      db/
        pool.js           connection pool ตัวเดียวทั้งแอป
        migrations/       node-pg-migrate — ไฟล์ละหนึ่งการเปลี่ยนแปลง
        seed/             ยัดข้อมูลจาก src/data/mock/ เข้าดาต้าเบส
      auth/
        password.js       argon2id hash/verify
        tokens.js         ออก/ตรวจ access + refresh token
        middleware.js     requireAuth · requirePermission("farm.manage")
        permissions.js    **คัดลอกกติกาจาก src/lib/auth/roles.js มาตรง ๆ**
      modules/            หนึ่งโฟลเดอร์ = หนึ่งเรื่อง
        farms/            route.js · service.js · queries.sql.js
        barns/
        readings/         ค่าเซนเซอร์ + ชั้นสรุป
        alerts/
        equipment/
        logs/             บันทึกประจำวัน + ปรับจำนวนสุกร
        users/            บัญชี + ค่าตั้ง + เลย์เอาต์
      jobs/
        alertEngine.js    อ่านค่าใหม่ → เทียบเกณฑ์ → เขียนแจ้งเตือน
        retention.js      บีบอัด/ลบข้อมูลดิบเก่า
      lib/
        error.js          AppError + ตัวจับ error กลาง
        validate.js       ห่อ zod ให้คืน 400 รูปแบบเดียวกันทุกเส้นทาง
    simulator/
      index.js            ตัวจำลองเซนเซอร์ (โปรเซสแยก)
    test/
```

**กติกาสำคัญ: `server/src/auth/permissions.js` ต้องเป็นกติกาชุดเดียวกับ `src/lib/auth/roles.js`**
คีย์เดียวกันเป๊ะ (`farm.manage` · `equipment.control` · `system.settings` · `record.write` · `prefs.write`)
หน้าบ้านใช้เพื่อ **ปิดปุ่มให้รู้ว่าทำไม่ได้** · หลังบ้านใช้เพื่อ **กันจริง**
ถ้าสองที่ไม่ตรงกัน จะเกิดปุ่มที่กดได้แต่เซิร์ฟเวอร์ปฏิเสธ (หรือแย่กว่านั้น — ปุ่มที่ปิดไว้แต่ยิง API ตรงได้)

## 4. ผู้ใช้ สิทธิ์ และการเข้าสู่ระบบ

### สิ่งที่ต้องเปลี่ยนจากของเดิม

| ตอนนี้ | หลังมี backend |
|---|---|
| `accounts.js` ตรวจ `admin`/`1234` ในเบราว์เซอร์ | `POST /api/auth/login` ตรวจกับ `app_user.password_hash` (argon2id) |
| สิทธิ์เดาจากรหัสผู้ใช้ (`admin` = แอดมิน) | สิทธิ์มาจากคอลัมน์ `app_user.role` เท่านั้น |
| เก็บ `{userId, roleId}` ใน localStorage | access token อายุสั้นในหน่วยความจำ + refresh token ใน httpOnly cookie |
| **เก็บรหัสผ่านไว้ในเครื่องเพื่อกดทีเดียวเข้า** | **เลิกเก็บ** — refresh token ทำหน้าที่นี้แทนและเพิกถอนได้ |
| บันทึกเข้าใช้งานอยู่ในเครื่องใครเครื่องมัน | `auth_event` ในดาต้าเบส — ผู้ดูแลเห็นของทุกเครื่อง |

> **จุดที่ต้องรื้อแน่ ๆ**: ตอนนี้ `swine-sync:remembered` เก็บรหัสผ่านแบบอ่านออกได้
> (ผู้ใช้เลือกเองเพื่อให้กดทีเดียวเข้า — ดู T1.119) พอมี backend ให้เปลี่ยนเป็นเก็บแค่
> **รหัสผู้ใช้ไว้เติมในช่อง** ส่วน "กดทีเดียวเข้า" มาจาก refresh token ที่ยังไม่หมดอายุ
> ได้ผลเหมือนเดิมเป๊ะในสายตาผู้ใช้ แต่รหัสผ่านไม่เคยลงเครื่อง และแอดมินสั่งเตะออกได้จากส่วนกลาง

### โทเคน

```
access token   JWT อายุ 15 นาที เก็บในหน่วยความจำของหน้าเว็บ (ไม่ลง localStorage)
               payload: { sub: user_id, role: "admin"|"user", company_id }
refresh token  สุ่ม 32 ไบต์ อายุ 30 วัน เก็บใน httpOnly + Secure + SameSite=Lax cookie
               ฝั่งเซิร์ฟเวอร์เก็บเฉพาะ hash ไว้ในตาราง session (เพิกถอนได้ทีละอัน)
```

**ทำไม access token ไม่ลง localStorage** — สคริปต์อะไรก็อ่าน localStorage ได้
ถ้ามี XSS สักจุดเดียวโทเคนหลุดทันที เก็บในตัวแปรของแอปแล้วขอใหม่ผ่าน refresh cookie
ตอนรีเฟรชหน้าจะปลอดภัยกว่า และผู้ใช้ไม่รู้สึกต่างเลย

**หมุน refresh token ทุกครั้งที่ใช้** (rotation) — ถ้าโทเคนเก่าถูกใช้ซ้ำแปลว่ามีคนขโมยไป
ให้ยกเลิกทั้งสายของ session นั้นทันที

### สิทธิ์บังคับสองชั้น เหมือนที่หน้าบ้านทำอยู่แล้ว

```js
// เส้นทางที่เขียนข้อมูลต้องผ่านสองด่านเสมอ
router.post("/farms", requireAuth, requirePermission("farm.manage"), createFarm);
```

และ**ในตัว service ต้องเช็กขอบเขตข้อมูลอีกที** — ผู้ใช้เห็นเฉพาะฟาร์มที่ตัวเองมีสิทธิ์
(`user_farm`) ไม่ใช่ว่ามี `farm.manage` แล้วแก้ฟาร์มของบริษัทอื่นได้ สองเรื่องนี้คนละเรื่องกัน

### ผู้ใช้สร้างในระบบเอง — แล้วคนแรกมาจากไหน

ไม่ต่อ AD/SSO ตามที่ตกลงกันไว้ จึงต้องมีทางสร้างบัญชีสองทาง:

- **แอดมินคนแรก** มาจาก seed ตอนตั้งระบบ อ่านรหัสจาก env (`SEED_ADMIN_USER` / `SEED_ADMIN_PASSWORD`)
  แล้ว **บังคับเปลี่ยนรหัสผ่านตอนเข้าครั้งแรก** (`app_user.must_change_password`)
  ไม่งั้นรหัสตั้งต้นจะอยู่ยงคงกระพันเหมือน `1234` ในรุ่นสาธิตตอนนี้
- **คนต่อ ๆ ไป** แอดมินสร้างให้ผ่าน `POST /api/users` — เพิ่มหน้าจอจัดการผู้ใช้เข้ามาใหม่ในแอป
  (**หน้านี้ยังไม่มีในหน้าบ้าน ต้องทำเพิ่ม** — เป็นงานเดียวที่ backend รอบนี้บังคับให้เพิ่มหน้าใหม่)

| Method | Path | สิทธิ์ |
|---|---|---|
| GET/POST | `/users` | `system.settings` |
| PATCH | `/users/:id` | `system.settings` (แก้ชื่อ · สิทธิ์ · เปิด/ปิดบัญชี) |
| POST | `/users/:id/reset-password` | `system.settings` |
| POST | `/me/password` | ตัวเอง |

**ห้ามมี `DELETE /users/:id`** — ตั้ง `active=false` แทน เพราะ `barn_log.created_by`
กับ `alert.acked_by` ต้องยังชี้ไปหาคนที่ทำได้เสมอ ลบคนทิ้งแล้วประวัติจะอ่านไม่รู้เรื่อง

### ⚠️ คำที่ห้ามสลับ

**"สิทธิ์" (`app_user.role` = admin | user)** = ทำอะไรได้ — เรื่องความปลอดภัย
**"ธีมบทบาท" (`user_pref.prefs.roleTheme` = สัตวบาล/สัตวแพทย์/ผู้จัดการ/…)** = เห็นอะไรก่อน — เป็นความชอบส่วนตัว

เอกสาร `DATABASE.md` ฉบับก่อนเขียน `app_user.role` เป็น `owner|manager|vet|technician|staff`
ซึ่ง **ผิด** — นั่นคือธีมบทบาท ไม่ใช่สิทธิ์ ถ้าทำตามนั้นจะกลายเป็น "เปลี่ยนธีมแล้วได้สิทธิ์เพิ่ม"
แก้ในฉบับปรับปรุงแล้ว

## 5. หน้าตา API

ทุกเส้นทางขึ้นต้น `/api` · ตอบ JSON · error รูปแบบเดียวกันหมด:
`{ error: { code, message, details? } }`

### บัญชี

| Method | Path | ทำอะไร | สิทธิ์ |
|---|---|---|---|
| POST | `/auth/login` | ตรวจรหัสผ่าน → ออก token คู่ | — |

## 6. ตัวจำลองเซนเซอร์

```
server/simulator/index.js  →  POST /api/ingest/readings  →  sensor_reading
                                       ↑
                              (วันหน้า) MQTT bridge
```

**ประเด็นสำคัญของการออกแบบส่วนนี้: ตัวจำลองต้องเข้าทางเดียวกับอุปกรณ์จริง**
ไม่ใช่เขียนลงตารางตรง ๆ — ถ้าเขียนตรงเข้าดาต้าเบส วันที่เปลี่ยนไปใช้อุปกรณ์จริงจะพบว่า
เส้นทางรับข้อมูลจริงไม่เคยถูกทดสอบเลยสักครั้ง

```
POST /api/ingest/readings
Authorization: Bearer <device token>       ← คนละชนิดกับ token ของผู้ใช้
{
  "deviceCode": "F-CNX-A1-SENSOR-A",
  "at": "2026-08-24T10:00:00Z",
  "readings": { "temp_c": 27.4, "humidity": 71, "nh3": 12 }
}
```

รับเป็น batch ได้ · idempotent ด้วย `(device_id, at, metric)` — ส่งซ้ำไม่เกิดแถวซ้ำ
(อุปกรณ์จริงที่เน็ตหลุดแล้วส่งย้อนหลังจะทำแบบนี้เสมอ)

**ตัวจำลองสร้างค่ายังไง** — ยกตรรกะจาก `src/data/mock/climate.js` มาใช้เลย
(`dayShape()` + สุ่มแบบ seed) เพราะมันสมจริงพอแล้ว: อุณหภูมิขึ้นกลางวันลงกลางคืน ·
ความชื้นสวนทาง · โรงเรือนเดิมได้ค่าชุดเดิม แล้วเพิ่มสองอย่างที่ mock ไม่มี:

- **เดินตามเวลาจริง** ทุก 1 นาที (ปรับได้ด้วย env) ไม่ใช่สร้างทั้งชุดทีเดียว
- **โหมดสร้างเหตุการณ์** — สั่งให้โรงเรือนหนึ่งร้อนขึ้นเรื่อย ๆ ได้ เพื่อทดสอบว่า
  เครื่องคิดแจ้งเตือนทำงานจริง ไม่ใช่รอให้บังเอิญเกิด

```bash
npm run sim                        # เดินปกติทุกโรงเรือน
npm run sim -- --backfill 30d      # ยัดย้อนหลัง 30 วัน ให้กราฟมีของดูทันที
npm run sim -- --spike F-KKN-A3    # ดันอุณหภูมิโรงเรือนนี้ให้ทะลุเกณฑ์
```

`--backfill` สำคัญกว่าที่คิด — ไม่มีมันแล้วต้องรอ 30 วันจริงถึงจะเห็นว่าหน้ากราฟ 30 วันทำงานถูก

## 7. เครื่องคิดแจ้งเตือน

โปรเซสเบื้องหลัง เดินทุก 1 นาที:

```
1. อ่านค่าล่าสุดของทุกโรงเรือน (v_barn_current)
2. เทียบกับ alert_rule ที่ enabled (global → farm → barn — เจาะจงกว่าชนะ)
3. ผิดเกณฑ์และยังไม่มีแจ้งเตือนเปิดค้างของ (barn, metric) นั้น → เขียนแถวใหม่
4. กลับเข้าเกณฑ์แล้วและมีแถวเปิดค้างอยู่ → ปิดอัตโนมัติ พร้อมบันทึกว่าปิดเอง
```

**สามเรื่องที่ต้องระวัง ไม่งั้นแจ้งเตือนจะกลายเป็นสิ่งที่คนปิดหูปิดตาใส่**

- **ค่ากลับไปกลับมา (flapping)** — อุณหภูมิแกว่งรอบเส้นเกณฑ์แล้วเตือน 40 ครั้งใน 1 ชม.
  แก้ด้วย `alert_rule.hold_minutes` — ต้องผิดเกณฑ์ต่อเนื่องกี่นาทีถึงจะนับ
  (ค่าตั้งต้น 10 นาที · ข้อความในหน้าจอตอนนี้ก็เขียนว่า "สูงเกิน 31°C **ต่อเนื่อง 2 ชม.**" อยู่แล้ว)
- **เซนเซอร์เงียบ ≠ ทุกอย่างปกติ** — ไม่มีค่าเข้ามาเกิน N นาที ต้องเปิดแจ้งเตือน
  หมวด `sensor` เอง ไม่ใช่ปล่อยให้หน้าจอโชว์ค่าเก่าค้างเหมือนยังปกติดี
- **เกณฑ์เปลี่ยนย้อนหลังไม่ได้** — แถวแจ้งเตือนต้องเก็บ `value` กับ `threshold` ที่ใช้ตัดสิน
  ณ ตอนนั้นไว้ด้วย ไม่งั้นแอดมินขยับเกณฑ์แล้วประวัติเก่าอ่านไม่รู้เรื่อง

รอบแรกให้เดินใน**โปรเซสเดียวกับ API ก่อน** (`setInterval` ตอนบูต) พอมีหลาย instance
ค่อยแยกออกไปพร้อมล็อก (`pg_advisory_lock`) กันไม่ให้สองตัวเขียนซ้ำ

### ⚠️ เซิร์ฟเวอร์ต้องไม่เก็บ "ข้อความแจ้งเตือน" เป็นภาษาไทย

**จุดที่ร่างแรกออกแบบผิด และต้องแก้ก่อนเขียนโค้ด**

ตอนนี้ `causesOf()` ใน `data/mock/alerts.js` ประกอบข้อความไทยด้วย template literal:

```js
title: `อุณหภูมิสูงกว่าเกณฑ์ ${over.toFixed(1)} °C`
detail: `วัดได้ ${barn.tempC} °C (เกณฑ์ ${limits.tempMin}–${limits.tempMax} °C) — เพิ่มรอบพัดลม…`
```

ถ้าย้ายตรรกะนี้ไปเซิร์ฟเวอร์ตรง ๆ แล้วเก็บ `title`/`detail` เป็นข้อความสำเร็จรูป
**แจ้งเตือนจะเป็นภาษาไทยตลอดกาล แปลเป็นอังกฤษ/จีนไม่ได้อีกเลย** —
ซึ่งขัดกับระบบ 3 ภาษาที่ทำไว้แล้ว (T2.1) และแก้ทีหลังแปลว่าต้อง migrate แถวแจ้งเตือนทั้งหมด

**ที่ถูกคือเก็บ "รหัส + ตัวเลข" แล้วให้หน้าจอประกอบข้อความเอง**

```sql
alert(
  …,
  code   text,    -- temp_over | humidity_high | nh3_high | pig_sick | pig_missing
                  -- | feed_low | water_low | sensor_offline
  params jsonb,   -- { over: 3.2, value: 31.2, min: 22, max: 28 }
  -- ไม่มีคอลัมน์ title/detail อีกต่อไป
)
```

หน้าจอเรียก `t("alert.temp_over.title", params)` ผ่านระบบแปลเดิมที่มีอยู่แล้ว
**ได้ของแถมสองอย่าง**: ผู้ใช้เปลี่ยนภาษาแล้วแจ้งเตือนเก่าเปลี่ยนตาม (ไม่ใช่ค้างภาษาที่บันทึกไว้)
และแก้คำผิดในข้อความทีเดียวมีผลกับทุกแถวย้อนหลัง ไม่ต้อง UPDATE ทั้งตาราง

**สิ่งที่ต้องทำเพิ่มในหน้าบ้าน**: ย้ายข้อความจาก `causesOf()` เข้าไฟล์แปล
พร้อมคำแปล en/zh (ตอนนี้ข้อความแจ้งเตือนยังไม่ได้ผ่าน `t()` เลยสักอัน — ถือเป็นหนี้ที่ค้างอยู่แล้ว
ไม่ใช่งานที่ backend สร้างขึ้นใหม่)

## 7.1 เวลาและโซนเวลา — เรื่องเล็กที่พังเงียบ ๆ

**อีกจุดที่ร่างแรกไม่ได้พูดถึงเลย และเป็นบั๊กที่หาเจอยากที่สุดเวลาเกิด**

mock ตอนนี้เก็บเวลาแบบ **ไม่มีโซนเวลา**: `"2026-08-03T10:18:00"`
JavaScript อ่านค่านี้เป็น**เวลาท้องถิ่นของเครื่องที่เปิดหน้าเว็บ** ตอนนี้ไม่มีปัญหา
เพราะทุกคนอยู่ไทยและข้อมูลเป็นค่าคงที่ในไฟล์ แต่พอมีเซิร์ฟเวอร์จริง:

| ถ้าทำแบบนี้ | จะเกิดอะไร |
|---|---|
| เก็บเป็น `timestamp` (ไม่มีโซน) | เซิร์ฟเวอร์ใน Docker เป็น UTC · กราฟจะเลื่อนไป **7 ชั่วโมง** |
| ส่ง JSON เป็นข้อความไม่มีโซน | เบราว์เซอร์แปลผิดแบบเดียวกัน โดยไม่มี error ให้เห็น |

**กติกาสามข้อ ห้ามยกเว้น**

1. **ทุกคอลัมน์เวลาเป็น `timestamptz`** ไม่ใช่ `timestamp` — ไม่มีข้อยกเว้น
2. **API ส่งออกเป็น ISO 8601 พร้อมโซนเสมอ** (`2026-08-03T03:18:00Z`)
   ให้ `Intl.DateTimeFormat` ฝั่งหน้าจอแปลงเป็นเวลาไทยเอง ซึ่ง `lib/format.js` ทำถูกอยู่แล้ว
3. **ตั้ง `TZ=Asia/Bangkok` ใน container ของ api** — ไม่ใช่เพื่อการเก็บข้อมูล
   (นั่นเป็น UTC เสมอ) แต่เพื่อให้ log กับการสรุป "รายวัน" ตัดวันตรงกับวันของคนไทย
   ไม่ใช่ตัดตอน 7 โมงเช้า

**ข้อ 3 สำคัญกว่าที่คิด** — `sensor_daily` ที่ `time_bucket('1 day', at)` โดยไม่ระบุโซน
จะตัดวันตาม UTC แปลว่า "ค่าเฉลี่ยวันที่ 3 ส.ค." จริง ๆ คือ 3 ส.ค. 07:00 ถึง 4 ส.ค. 07:00
ต้องเขียนเป็น `time_bucket('1 day', at, 'Asia/Bangkok')` ให้ชัด

## 8. การสั่งอุปกรณ์ — ทำไมไม่ใช่ `PUT /fans/1 {on:true}`

พัดลมเป็นของจริงที่หมุนอยู่ในโรงเรือน สั่งแล้วมันอาจไม่ทำตาม (ไฟดับ · เน็ตหลุด · เบรกเกอร์ตัด)
ระบบจึงต้องแยก **"สิ่งที่สั่ง"** ออกจาก **"สิ่งที่เป็นอยู่จริง"**

```
POST /api/barns/:id/commands
{ "deviceCode": "FAN 3", "action": "on", "hz": 50 }
→ 202 Accepted { commandId, status: "pending" }
```

```
device_command(id, barn_id, device_id, action, params jsonb,
               requested_by, requested_at,
               status,          -- pending | sent | confirmed | failed | timeout
               confirmed_at, error)
```

ได้สามอย่างที่วิธี `PUT` ตรง ๆ ให้ไม่ได้:

1. **หน้าจอบอกความจริงได้** — "กำลังสั่ง…" แล้วค่อยเป็น "เปิดแล้ว" หรือ "สั่งไม่สำเร็จ"
   ไม่ใช่แสดงว่าเปิดทั้งที่พัดลมไม่ได้หมุน
2. **ตรวจสอบย้อนหลังได้** — ค่าไฟเดือนนี้พุ่ง เปิดดูได้ว่าใครสั่งเปิดพัดลมครบ 5 ตัวตอนตีสอง
3. **สั่งซ้ำได้อย่างปลอดภัย** — เน็ตหลุดตอนกด กดใหม่ไม่เกิดคำสั่งซ้อน

ตอนยังไม่มีตู้ควบคุมจริง ให้ตัวจำลอง "รับคำสั่ง" แล้วตอบ `confirmed` หลัง 1–2 วินาที
หน้าจอจะได้เดินครบวงจรจริงตั้งแต่วันแรก

| คีย์ | ไปไหน | เหตุผล |
|---|---|---|
| `swine-sync:auth` | **หายไป** → access token ในหน่วยความจำ + refresh cookie | ปลอดภัยกว่าและเพิกถอนได้ |
| `swine-sync:remembered` | **เหลือแค่รหัสผู้ใช้** (ไม่เก็บรหัสผ่านแล้ว) | "กดทีเดียวเข้า" มาจาก refresh token แทน |
| `swine-sync:auth-log` | → ตาราง `auth_event` | ตอนนี้เห็นแค่เครื่องตัวเอง ไม่ใช่บันทึกจริง |
| `swine-sync:records` | → `farm` / `barn` โดยตรง | ชั้น "ผู้ใช้แก้ทับ" หมดหน้าที่เมื่อมีของจริง |
| `swine-sync:adjust` | → `pig_count_adjust` | คนอื่นต้องเห็นด้วย และต้องรู้ว่าใครปรับ |
| `swine-sync:snapshots` | → `camera_snapshot` + ไฟล์ใน object storage | ภาพต้องอยู่ต่อแม้เปลี่ยนเครื่อง |
| `swine-sync:settings` | **แยกสองส่วน** → `user_pref` (ของตัวเอง) + `system_setting` (เกณฑ์/ค่าไฟ) | นี่คือต้นเหตุ "สองคนเห็นคนละเลข" |
| `swine-sync:layouts` | → `layout_preset` | ย้ายเครื่องแล้วเลย์เอาต์ตามไป |
| `swine-sync:theme` · `:lang` | → `user_pref.prefs` | อยู่ก้อนเดียวกับค่าตั้งอื่นของคนคนนั้น |

**สองอย่างที่ควร "อยู่ในเครื่องต่อไป"** แม้มี backend แล้ว:
ภาษาที่เลือกไว้ก่อนล็อกอิน (หน้าล็อกอินยังไม่รู้ว่าใครเปิดอยู่) และรหัสผู้ใช้ที่จดจำไว้
สองอันนี้เป็นของ "เครื่องนี้" จริง ๆ ไม่ใช่ของบัญชี

**ทางย้ายที่ไม่ทำให้ของเก่าหาย** — ตอนล็อกอินสำเร็จครั้งแรกหลังอัปเดต ถ้าเจอ
`swine-sync:settings` / `:layouts` ในเครื่องแล้วฝั่งเซิร์ฟเวอร์ยังว่าง ให้ยิงขึ้นไปเก็บให้อัตโนมัติ
แล้วค่อยลบของในเครื่อง ผู้ใช้จะไม่รู้สึกว่าค่าที่ตั้งไว้หายไป

## 10. ต่อหน้าบ้านยังไงโดยแทบไม่แก้หน้าจอ

โปรเจกต์นี้กันขอบเขตไว้ดีมาแล้ว — **ไม่มีหน้าไหนแตะ mock ตรง ๆ มันเรียกผ่านฟังก์ชันเสมอ**
เปลี่ยนแค่ข้างในฟังก์ชันพวกนี้ให้ไปเรียก API แทน แล้วหน้าจอไม่ต้องแก้เลย

| ฟังก์ชันเดิม | เปลี่ยนเป็น |
|---|---|
| `farms` · `summarizeFarms()` | `GET /api/farms` |
| `getFarmBarns(farmId)` | `GET /api/farms/:id/barns` |
| `getBarnTrend(f,b,hours)` | `GET /api/barns/:id/readings?range=24h` |
| `getBarnDaily(f,b,days)` | เหมือนกัน แค่ `range=7d` |
| `getSensorMap(f,b)` | `GET /api/barns/:id/sensor-map` |
| `getEquipment/getElectrical` | `GET /api/barns/:id/systems` |
| `setFan/setPump` (`lib/equipment.js`) | `POST /api/barns/:id/commands` |
| `allAlerts(limits)` | `GET /api/alerts?status=open` (**เลิกส่ง limits — เซิร์ฟเวอร์รู้เกณฑ์เอง**) |
| `useRecords()` | `POST/PATCH/DELETE /api/farms` · `/api/barns` |
| `useAdjust()` | `/api/barns/:id/pig-count` |
| `useSnapshots()` | `/api/barns/:id/snapshots` |
| `useSettings()` | `/api/me/prefs` + `/api/settings/system` |
| `authenticate()` (`lib/auth/accounts.js`) | `POST /api/auth/login` — **ลบไฟล์ทิ้งทั้งไฟล์** |

**สิ่งที่ต้องเพิ่มในหน้าบ้านจริง ๆ มีสามอย่าง** (นอกเหนือจากแก้ข้างในฟังก์ชัน):

1. **สถานะ "กำลังโหลด" กับ "โหลดไม่สำเร็จ"** — ตอนนี้ข้อมูลมาทันทีเสมอเพราะเป็นค่าคงที่ในไฟล์
   ทุกการ์ดต้องรับได้ว่าข้อมูลยังไม่มา หรือมาไม่ได้ (ควรทำเป็น component กลางใบเดียว ไม่ใช่ทำทีละหน้า)
2. **ตัวเรียก API กลาง** (`src/lib/api/client.js`) — ใส่ token · ต่ออายุอัตโนมัติเมื่อ 401 ·
   แปลง error เป็นข้อความไทยที่ผ่าน `t()`
3. **ยอมรับว่าข้อมูลอาจเปลี่ยนระหว่างเปิดหน้าอยู่** — โพลทุก 30–60 วินาทีสำหรับค่าปัจจุบัน
   (SSE/WebSocket ไว้ทีหลัง ยังไม่จำเป็นในรอบแรก)

**ข้อดีของการที่โครงหน้าบ้านเป็นแบบนี้อยู่แล้ว**: ต่อทีละหน้าได้ ไม่ต้องเปลี่ยนพร้อมกันทั้งแอป
หน้าที่ยังไม่ต่อก็ใช้ mock ต่อไปโดยไม่พัง

## 11. ลำดับลงมือ

แต่ละขั้นจบแล้ว**ใช้งานได้จริงทันที** ไม่ใช่ต้องทำครบทุกขั้นถึงจะเห็นผล

| # | ทำอะไร | ได้อะไรทันที |
|---|---|---|
| 1 | โครงเซิร์ฟเวอร์ + `app_user` + auth + `user_pref` | เข้าระบบด้วยรหัสผ่านจริง · ค่าตั้งตามตัวคนข้ามเครื่อง · **สิทธิ์กันได้จริง** |
| 2 | `farm` · `barn` · `device` + seed จาก mock + ต่อหน้าฟาร์ม/โรงเรือน | เพิ่ม/แก้ฟาร์มแล้วทุกคนเห็นตรงกัน |
| 3 | `sensor_reading` + ชั้นสรุป + ตัวจำลอง + ต่อหน้าอุณหภูมิ/สภาพแวดล้อม | กราฟย้อนหลังจริง ไม่ใช่ค่าคงที่ |
| 4 | `alert_rule` + `alert` + เครื่องคิดแจ้งเตือน | **จบปัญหาเลขไม่ตรงกันถาวร** + กดรับเรื่องได้ |
| 5 | `barn_log` · `pig_count_adjust` · `camera_snapshot` | คนหน้างานบันทึกแล้วไม่หาย คนอื่นเห็นด้วย |
| 6 | `device_command` + ต่อการ์ดควบคุม | สั่งพัดลมได้จริงพร้อมประวัติ |
| 7 | อาหาร · การเงิน | ทำทีหลังได้ เป็นข้อมูลรายเดือน ไม่เร่ง |

**ขั้น 1 กับ 4 คุ้มที่สุด** — ขั้น 1 แก้เรื่องสิทธิ์ปลอมได้ทันที ขั้น 4 แก้ปัญหาที่กวนใจที่สุด
ในเชิงใช้งาน ส่วนขั้น 3 หนักที่สุดแต่ทำครั้งเดียวแล้วจบ

## 12. ภาพจากกล้อง

ไม่เก็บไฟล์ภาพลงดาต้าเบส — เก็บใน **MinIO** ซึ่งเป็นอีก service ใน compose
พูดภาษาเดียวกับ S3 ทุกอย่าง (SDK ตัวเดียวกัน) วันหลังอยากย้ายขึ้น S3 จริงเปลี่ยนแค่ endpoint

```
POST /api/barns/:id/snapshots
  → เซิร์ฟเวอร์บันทึกภาพลง MinIO ที่ snapshots/{barnId}/{yyyy}/{mm}/{id}.jpg
  → เขียนแถว camera_snapshot เก็บแค่ URL กับค่าที่ AI นับได้ตอนนั้น
```

**ทำไมไม่ยัดลงดาต้าเบส** — backup ของดาต้าเบสจะบวมจนคืนค่ายากและช้า
และ Postgres ไม่ได้ถูกออกแบบมาเสิร์ฟไฟล์ไบนารีให้เบราว์เซอร์

## 13. รันทุกอย่างบน Docker

รันบนเซิร์ฟเวอร์ของโครงการเอง ไม่ใช่คลาวด์ — compose ไฟล์เดียวขึ้นครบทั้งระบบ

```
docker compose up -d
   ├── db          timescale/timescaledb-ha:pg16     ← ข้อมูลทั้งหมด
   ├── minio       minio/minio                       ← ไฟล์ภาพจากกล้อง
   ├── api         server/  (node:22-alpine)         ← Express + งานเบื้องหลัง
   ├── web         nginx:alpine                      ← หน้าบ้านที่ build แล้ว + reverse proxy
   └── sim         server/simulator/  (profile: dev) ← ตัวจำลองเซนเซอร์
```

### โครงไฟล์

```
cpf_dashboard/
  docker-compose.yml           ใช้จริง
  docker-compose.dev.yml       ทับด้วย override — hot reload + เปิดพอร์ต db ให้ต่อจากเครื่องได้
  .env.example                 ตัวแปรทั้งหมดพร้อมคำอธิบาย (ห้าม commit .env ตัวจริง)
  Dockerfile.web               build หน้าบ้านด้วย vite แล้วเสิร์ฟด้วย nginx
  server/Dockerfile            api + simulator ใช้ image เดียวกัน ต่างที่คำสั่งตอนรัน
  ops/
    nginx.conf                 เสิร์ฟไฟล์ static + proxy /api
    backup.sh                  pg_dump รายวัน
```

### หน้าบ้านคุยกับ API ยังไง

**nginx เสิร์ฟทั้งหน้าเว็บและ proxy `/api` ไปที่ container `api`** — เบราว์เซอร์เห็นเป็น origin
เดียวกันหมด จึง**ไม่มีปัญหา CORS และ cookie ของ refresh token ทำงานได้ตรงไปตรงมา**
(ถ้าแยกโดเมนกัน ต้องตั้ง `SameSite=None; Secure` ซึ่งพ่วงเรื่อง HTTPS มาอีกกอง)

```nginx
location /api/ { proxy_pass http://api:3000/api/; }
location /     { try_files $uri /index.html; }   # ให้ react-router จัดการเส้นทางเอง
```

บรรทัด `try_files` สำคัญ — ไม่มีมันแล้วผู้ใช้กด refresh ที่ `/dashboard/farms` จะได้ 404
เพราะ nginx ไปหาไฟล์ชื่อนั้นจริง ๆ

### สามเรื่องที่ต้องมีตั้งแต่วันแรก ไม่ใช่ค่อยเติม

**1. healthcheck + `depends_on: condition: service_healthy`**
Postgres ใช้เวลาบูตหลายวินาที ถ้า api ขึ้นก่อนแล้วต่อไม่ติดจะตายทันที
แล้วคนจะไปโทษว่า "โค้ดพัง" ทั้งที่แค่ขึ้นเร็วไป

```yaml
db:
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
    interval: 5s
    retries: 10
api:
  depends_on:
    db: { condition: service_healthy }
  restart: unless-stopped
```

**2. migration รันตอน api บูต** (`npm run migrate up && node src/index.js`)
ไม่ใช่ให้คนจำว่าต้องรันเอง — `docker compose up` แล้วต้องใช้งานได้เลย
node-pg-migrate จำได้ว่ารันไปถึงไหนแล้ว รันซ้ำไม่เกิดอะไรขึ้น

**3. named volume สำหรับข้อมูล** — `db-data` กับ `minio-data`
ไม่มีสองอันนี้แล้ว `docker compose down -v` ทีเดียวข้อมูลหายเกลี้ยง

### ตัวแปรที่ต้องตั้ง

```bash
POSTGRES_PASSWORD=            # ตั้งเอง อย่าใช้ค่าตัวอย่าง
JWT_SECRET=                   # openssl rand -base64 48
MINIO_ROOT_PASSWORD=
SIM_INTERVAL_SECONDS=60       # ตัวจำลองเดินทุกกี่วินาที
RAW_RETENTION_DAYS=90         # เก็บข้อมูลดิบกี่วัน (ดูข้อ 14)
COMPRESS_AFTER_DAYS=7
```

### backup — เรื่องที่ระบบ on-prem มักลืมจนสาย

รันบนเครื่องตัวเองแปลว่า**ไม่มีใครสำรองข้อมูลให้** ต้องตั้งเองตั้งแต่วันแรก

```bash
# ops/backup.sh — ตั้ง cron รายวัน เก็บไว้ 30 ชุด
docker compose exec -T db pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB" \
  > "/backup/swine-$(date +%F).dump"
```

**และต้องลองกู้คืนจริงอย่างน้อยหนึ่งครั้ง** — backup ที่ไม่เคยกู้คืนสำเร็จ ไม่นับว่ามี backup

## 14. เก็บข้อมูลย้อนหลังนานแค่ไหน (ยังไม่กำหนด — จึงทำให้แก้ทีหลังได้)

ยังไม่มีข้อกำหนดว่าต้องเก็บกี่ปี **จึงห้ามฝังตัวเลขลงในโค้ด** ให้เป็นค่าตั้ง
(`RAW_RETENTION_DAYS` / `COMPRESS_AFTER_DAYS`) ที่แก้แล้วมีผลโดยไม่ต้องแก้โปรแกรม

### ค่าตั้งต้นที่เสนอ

| ชั้น | เก็บนานแค่ไหน | เหตุผล |
|---|---|---|
| ข้อมูลดิบรายนาที | 90 วัน | หน้าจอย้อนหลังไกลสุดแค่ 48 ชม. · เก็บ 90 วันเผื่อไล่หาสาเหตุย้อนหลังได้สบาย |
| รายชั่วโมง | 2 ปี | ใช้ทำกราฟย้อนหลังยาว |
| **รายวัน** | **ตลอดไป** | เล็กมากและใช้เทียบปีต่อปี — อันนี้ไม่ควรลบไม่ว่ากรณีใด |

### ประมาณการพื้นที่ (ตัวเลขคร่าว ๆ ไว้เลือกขนาดดิสก์)

จาก 38 โรงเรือน × ~10 ค่า × ทุก 1 นาที ≈ 200 ล้านแถว/ปี

| กรณี | พื้นที่/ปี |
|---|---|
| เก็บดิบไว้ทั้งหมด ไม่บีบอัด | **~30–50 GB** (รวม index) |
| บีบอัดหลัง 7 วัน + ลบดิบหลัง 90 วัน | **~5–8 GB** |
| เฉพาะรายวัน (139,000 แถว/ปี) | **< 50 MB** |

**ดิสก์ 500 GB อยู่ได้สบายหลายปีในทุกกรณี** ตัวเลขนี้เป็นการประมาณ ไม่ใช่ค่าที่วัดจริง —
พอมีข้อมูลจริงเดินสัก 1 สัปดาห์ให้วัดจาก `pg_total_relation_size()` แล้วคูณกลับ จะแม่นกว่ามาก

**ถ้าองค์กรมากำหนดทีหลังว่าต้องเก็บ 5 ปี** — เปลี่ยนแค่ `RAW_RETENTION_DAYS`
หรือถ้าดิสก์ไม่พอ ให้ย้ายข้อมูลเก่าออกไปเป็นไฟล์ (`COPY ... TO`) แล้วเก็บไว้นอกฐาน
โครงที่ออกแบบไว้รองรับทั้งสองทางโดยไม่ต้องแก้ตาราง

## 15. แรงที่ต้องใช้จริง และคำถามว่าจำเป็นแค่ไหน

### ประมาณการ (คนเดียวทำ · นับเฉพาะเวลาลงมือ ไม่รวมเวลาเรียนของใหม่)

| ขั้น | งาน | วันทำงาน |
|---|---|---|
| 1 | Docker compose + auth + ผู้ใช้ + ค่าตั้ง + **หน้าจัดการผู้ใช้ (หน้าใหม่)** | 5–8 |
| 2 | ฟาร์ม/โรงเรือน/อุปกรณ์ + seed + ต่อ 2 หน้า | 4–6 |
| 3 | เซนเซอร์ + ชั้นสรุป + ตัวจำลอง + ต่อหน้ากราฟ | 7–10 |
| 4 | เกณฑ์ + แจ้งเตือน + เครื่องคิด + **ย้ายข้อความแจ้งเตือนเข้าระบบแปล** | 5–7 |
| 5 | บันทึกประจำวัน + ปรับจำนวน + ภาพกล้อง + MinIO | 4–5 |
| 6 | สั่งอุปกรณ์ | 3–4 |
| 7 | อาหาร + การเงิน | 4–5 |
| — | **สถานะโหลด/โหลดไม่สำเร็จ ทุกการ์ดในแอป** | 4–6 |
| | **รวม** | **36–51 วันทำงาน ≈ 8–11 สัปดาห์** |

ตัวเลขนี้เป็นการประมาณ ไม่ใช่คำสัญญา — งานแบบนี้มักบานตรงส่วนที่ไม่ได้อยู่ในลิสต์
(ต่อ Docker ให้ขึ้นบนเครื่องจริง · เวลาเพี้ยน · ข้อมูลที่ seed แล้วไม่ตรงกับที่หน้าจอเคยแสดง)

### ทำน้อยกว่านี้ได้ไหม — ได้ และควรพิจารณา

**ข้อเท็จจริงที่ต้องพูดตรง ๆ: ตอนนี้ยังไม่มีเซนเซอร์จริงสักตัว**
ตัวเลข 200 ล้านแถว/ปี ที่ใช้ตัดสินใจเลือก TimescaleDB มาจากสมมติฐานว่าจะมีอุปกรณ์
38 โรงเรือนส่งค่าทุกนาที — ซึ่งยังไม่เกิดขึ้นและอาจไม่เกิดในเร็ว ๆ นี้

**ถ้าเป้าหมายคือ "ให้ระบบใช้งานได้จริงเร็วที่สุด"** ทำแค่นี้ก็ได้ของที่มีประโยชน์แล้ว:

| ทำ | ข้าม | ได้อะไร |
|---|---|---|
| ขั้น 1 + 2 + 4 + 5 | ขั้น 3 (เก็บค่าเซนเซอร์ย้อนหลัง) · ขั้น 6 · ขั้น 7 | สิทธิ์จริง · ข้อมูลฟาร์มร่วมกัน · แจ้งเตือนตรงกันทุกคน · บันทึกงานไม่หาย |

ข้ามขั้น 3 แปลว่าเก็บแค่ "ค่าล่าสุด" ของแต่ละโรงเรือน (ตารางเล็กมาก ไม่ต้องใช้ Timescale เลย)
กราฟย้อนหลังยังใช้ข้อมูลจำลองไปก่อน — **ประหยัดไป 7–10 วัน และตัดความซับซ้อนที่สุดออก**
แล้วค่อยเติมขั้น 3 ตอนที่มีเซนเซอร์จริงมาต่อ ซึ่งเป็นตอนที่ตัวเลข 200 ล้านแถวจะมีความหมายจริง ๆ

**ยังคงใช้ PostgreSQL ตั้งแต่แรก** และออกแบบตารางเผื่อไว้ตามเอกสารนี้
เพราะเพิ่ม TimescaleDB ทีหลังทำได้โดยไม่ต้องย้ายข้อมูล (`create_hypertable` กับตารางที่มีข้อมูลอยู่แล้วได้)
สิ่งที่ห้ามทำคือเปลี่ยนชนิดฐานข้อมูลทีหลัง — อันนั้นแพง

**ผมแนะนำให้ทำขั้น 1 ก่อนแล้วค่อยตัดสินใจอีกที** เพราะขั้น 1 จบแล้ว
จะรู้ด้วยตัวเองว่าจังหวะการทำงานเป็นยังไง แล้วประมาณขั้นที่เหลือได้แม่นกว่าที่ผมเดาให้ตอนนี้

## 16. เรื่องที่ยังเปิดอยู่

ห้าข้อที่เคยค้างได้คำตอบครบแล้ว เหลือสามเรื่องที่ค่อยตัดสินตอนลงมือได้

1. **HTTPS** — รันในวงแลนฟาร์มอาจใช้ http ก่อนได้ แต่ถ้าเปิดให้เข้าจากนอก
   ต้องมี TLS เพราะ refresh cookie ตั้ง `Secure` ไว้ (ใส่ caddy หรือ nginx + certbot เพิ่มอีกชั้น)
2. **ใครดูแลเซิร์ฟเวอร์** — on-prem ต้องมีคนคอยดู disk เต็ม/เครื่องดับ/ไฟดับ
   อย่างน้อยต้องมีคนที่รู้วิธี `docker compose logs` และรู้ว่า backup อยู่ที่ไหน
3. **หลาย instance ในอนาคต** — ตอนนี้เครื่องคิดแจ้งเตือนเดินในโปรเซสเดียวกับ API
   ถ้าวันหนึ่งขยายเป็นหลายตัว ต้องใส่ `pg_advisory_lock` กันเขียนซ้ำ (เขียนไว้ในข้อ 7 แล้ว)
