## 1. ระบบประกอบด้วยอะไร

```
เซนเซอร์ที่ฟาร์มกำแพงเพชร
   │
   │  ท่อรับค่าจากอุปกรณ์ — ของทีมอื่น ไม่อยู่ในขอบเขตเอกสารชุดนี้
   │
   ▼
swine-bridge  ──►  swine-db (PostgreSQL + TimescaleDB)  ◄──  swine-api :3000
                                                                  │
                                                                  ▼
                                                        หน้าเว็บ (vite) :5173
```

**ค่าเซนเซอร์มาจากไหน** — อุปกรณ์ที่ฟาร์มส่งค่าเข้าท่อรับข้อมูลที่ทีมอื่นดูแล
แล้ว `swine-bridge` อ่านจากท่อนั้นมาเขียนลงฐานข้อมูลของระบบนี้ทุก 30 วินาที
**ตัวท่อไม่ใช่ของโครงการนี้** ถ้าค่าใหม่ไม่เข้า ให้ไล่ตามข้อ 5 แล้วแจ้งทีมที่ดูแลท่อ

ขาดช่วงไหนคือ **หายช่วงนั้นถาวร** ดึงย้อนหลังกลับมาไม่ได้ และ**ไม่มีใครเตือน**
นอกจากดูเวลาอัปเดตล่าสุดบนหน้าจอ

**สองอย่างนี้โครงการนี้ไม่ได้เป็นเจ้าของ** — ตัวเซนเซอร์ · ท่อรับค่าจากอุปกรณ์
เป็นของอีกทีม ถ้าจะแก้ต้องคุยกับเขาก่อน

### ★ กติกาข้อมูลขององค์กร (ผู้ใช้ยืนยัน 25 ก.ย. 2569)

**ห้ามขนฐานข้อมูลหรือข้อมูลอื่นขององค์กรออกไปไว้ที่เครื่องอื่น**
ทางเดียวที่ได้รับอนุญาตให้เข้าถึงข้อมูลฟาร์มคือ **ดึงผ่าน API ที่ `https://lab.plotnexuslab.com/api`**
ซึ่งพี่เลี้ยงเป็นผู้จัดทำและดูแลสิทธิ์

★ กติกาข้อนี้เคยตัดแผนที่**ทำได้ในทางเทคนิค**ทิ้งไปทั้งแผนมาแล้ว
➜ ถ้าแผนใหม่ต้องย้ายข้อมูลออกนอกที่ที่มันอยู่ **ถามเจ้าของข้อมูลก่อนเสมอ**
ไม่ใช่ถามแค่ว่าทำได้ไหม

### ★ ถอยมาใช้ฐานในเครื่องชั่วคราวตอนกล่องดับ (29 ก.ย. 2569)

กล่อง `box-mew` ดับตั้งแต่ 25 ก.ย. เย็น ทำให้ **ล็อกอินไม่ได้เลย** เพราะฟอร์มเข้าสู่ระบบ
ต้องถามฐานข้อมูล จึงปิดบรรทัด `REMOTE_DATABASE_URL` ใน `.env` เพื่อถอยมาใช้ `swine-db` ในเครื่อง

```bash
# ถอยมาใช้ฐานในเครื่อง — ใส่ # หน้า REMOTE_DATABASE_URL ใน .env แล้ว
docker compose up -d api bridge

# กลับไปใช้ฐานของกล่อง — เอา # ออก แล้วสั่งเดิมอีกครั้ง
docker compose up -d api bridge
```

ตรวจว่าตอนนี้ต่อฐานไหนอยู่ (ถามที่ container ไม่ใช่เดาจาก `.env`)

```bash
docker exec swine-api sh -c 'echo $DATABASE_URL'
```

#### สลับกลับแล้วข้อมูลเป็นอย่างไร

| อะไร | สลับกลับแล้ว |
| --- | --- |
| `sensor_reading` | **รวมเองอัตโนมัติ** — unique key `(barn_id, metric, device_id, at)` กันแถวซ้ำ และสะพานหาจุดเริ่มจากค่าล่าสุดของฐานปลายทางแล้วอ่านซ้ำจากต้นทาง |
| `alert` | ไม่งอกเพิ่มที่เครื่องผู้พัฒนา เพราะสะพานที่นี่เป็นบท `sync` ไม่ได้คิดแจ้งเตือน |
| `barn_log` · `app_user` · `farm`/`barn` · `control_command` | **ค้างอยู่ที่เครื่องผู้พัฒนา ต้องย้ายเอง** |

➜ **ช่วงที่ถอยมาใช้ฐานในเครื่อง ให้หลีกเลี่ยงการกรอกบันทึกจริงหรือสร้างผู้ใช้/ฟาร์มใหม่**
ถ้าเลี่ยงไม่ได้ ให้จดไว้ว่าเพิ่มอะไรบ้าง แล้วย้ายขึ้นไปหลังสลับกลับ
(`barn_log` มี `client_id` กันซ้ำอยู่แล้วจึงย้ายซ้ำได้ ส่วนผู้ใช้กับฟาร์มต้องทำมือ — uuid ไม่ตรงกัน)

#### ผลพลอยได้

`api` รัน migration ตอนสตาร์ตเสมอ การสลับมาฐานในเครื่องจึงทำให้ตาราง
`control_device` · `control_command` (T1.284) ถูกสร้างที่นี่ด้วย — **ทดสอบด่านความปลอดภัย
ของคำสั่งอุปกรณ์ได้โดยไม่ต้องรอกล่อง** ล็อกอินด้วยบัญชีระดับผู้ควบคุมอุปกรณ์แล้วกดสวิตช์ที่หน้าสภาพแวดล้อม

### ★ ตัวเฝ้าระวังว่าเครื่องหลักยังอยู่ไหม (T1.285)

**25–28 ก.ย. 2569 กล่อง `box-mew` ดับไป 3 วันเต็มโดยไม่มีใครรู้**
มันเป็นเครื่องที่คิดแจ้งเตือนและส่งไลน์ พอมันดับ การแจ้งเตือนก็เงียบไปด้วย —
และ **"ไม่มีข้อความเข้ามา" หน้าตาเหมือน "ทุกอย่างปกติ" เป๊ะ**
นี่คือจุดบอดของระบบแจ้งเตือนทุกระบบ ตัวเฝ้าตัวนี้มีไว้ปิดจุดนั้นจุดเดียว

#### ทำอะไร / ไม่ทำอะไร

ทำ: เรียก `PRIMARY_HEALTH_URL` ทุก 5 นาที · พลาดติดกัน 3 ครั้งแล้วส่งไลน์บอก ·
เตือนซ้ำทุก 12 ชม. ถ้ายังไม่กลับมา · บอกอีกครั้งตอนกลับมา

**ไม่ทำ: ไม่รับหน้าที่แจ้งเตือนแทน** เพราะการคิดแจ้งเตือนต้องใช้ฐานข้อมูล
ซึ่งอยู่บนเครื่องที่ดับไปนั่นเอง จะทำแทนได้ต้องมีฐานที่สอง แล้วก็ต้องแก้ปัญหา
ฐานสองชุดไม่ตรงกันอีก — เป็นของที่ส่งมอบให้คนอื่นดูแลต่อยากและพังเงียบกว่าเดิม
ตัวนี้จึงแค่ **บอกคนให้รู้ภายในไม่กี่นาที** แล้วให้คนไปแก้

#### กฎข้อเดียวที่ห้ามละเมิด

**ห้ามให้มันแตะฐานข้อมูล** (มีเทสต์คุมไว้) เพราะสิ่งที่มันเฝ้าคือเครื่องที่ฐานอยู่
ถ้าพึ่งฐาน มันจะตายพร้อมกันและเงียบเหมือนเดิม สถานะจึงเก็บเป็นไฟล์ใน volume
และการส่งไลน์ยิงตรงไป `api.line.me` ไม่ผ่านอะไรเลย

#### ตั้งค่าที่ไหน

ใส่ใน `.env` ของ **เครื่องที่ไม่ใช่เครื่องหลัก** (วันนี้คือเครื่องผู้พัฒนา ที่รันสะพานบทบาท `sync`)
ไม่ตั้ง `PRIMARY_HEALTH_URL` = ไม่ทำงานเลย เครื่องหลักจึงไม่เฝ้าตัวเองซึ่งไม่มีประโยชน์

| ตัวแปร | ค่าที่ใช้อยู่ | หมายเหตุ |
| --- | --- | --- |
| `PRIMARY_HEALTH_URL` | `https://mew.plotnexuslab.com/api/health` | นับว่าตอบเฉพาะ HTTP 2xx |
| `PRIMARY_NAME` | `กล่อง box-mew` | ชื่อที่ขึ้นในข้อความ |
| `PRIMARY_CHECK_MIN` | `5` | ตรวจทุกกี่นาที |
| `PRIMARY_REMIND_MIN` | `1440` | ดับยาวแล้วเตือนซ้ำทุกกี่นาที — **วันละครั้ง** (เดิม 12 ชม. · ยืด 30 ก.ย. 2569) |
| `PRIMARY_WATCH_NOTIFY` | `0` = ยังไม่ส่งจริง | **สวิตช์ของตัวเอง ไม่ใช่ `LINE_NOTIFY`** |
| `PRIMARY_OWNER` | ว่าง | ชื่อ/ช่องทางของคนที่**มีสิทธิ์เปิดกล่อง** — ข้อความจะบอกให้ไปแจ้งคนนี้ ไม่ใช่ให้ไปกดเอง |

★ **ทำไมไม่ใช้ `LINE_NOTIFY`**: ค่านั้นแปลว่า "เครื่องนี้ไม่ใช่เครื่องที่ส่งแจ้งเตือน"
ซึ่งตั้งไว้กันส่งซ้ำ — แต่ตัวเฝ้า**ต้องรันบนเครื่องที่ไม่ใช่เครื่องแจ้งเตือนพอดี**
ผูกสองอย่างนี้เข้าด้วยกันเมื่อไร ตัวเฝ้าจะเงียบตลอดไปบนเครื่องเดียวที่ควรพูด

#### โควตาไลน์

ส่งเฉพาะตอนเปลี่ยนสถานะ + เตือนซ้ำ **วันละครั้ง** → ดับยาว 3 วันใช้ราว **4 ข้อความ
จาก 300/เดือน** (มีเทสต์คุมว่า 3 วันต้องไม่เกิน 5 ข้อความ และต้องไม่เงียบหายไปเลย)

★ **ทำไมยืดจาก 12 ชม. เป็นวันละครั้ง** (30 ก.ย. 2569) — คนที่ได้ข้อความ **แก้เองไม่ได้**
ต้องรอเจ้าของกล่อง (ดู T1.299) เตือนวันละสองครั้งจึงกลายเป็นเสียงรบกวนที่ทำให้คนเลิกอ่าน
ซึ่งอันตรายกว่าการเตือนน้อยลงหนึ่งครั้ง · ปรับกลับได้ที่ `PRIMARY_REMIND_MIN` โดยไม่ต้องแก้โค้ด

#### ตรวจว่ามันทำงานอยู่ไหม

```bash
docker exec swine-bridge cat /state/primary-watch.json
```

`status` = `up` / `down` / `unknown` · `fails` = พลาดติดกันกี่ครั้งแล้ว ·
`lastCheckAt` ต้องขยับทุก 5 นาที ถ้าไม่ขยับแปลว่าสะพานไม่เดิน

```bash
docker logs --tail 50 swine-bridge | grep -i "เครื่องหลัก"
```

### ★ ตัวเฝ้าระวังว่าข้อมูลยังไหลอยู่ไหม (T1.295)

**29 ก.ย. 2569 ข้อมูลเซนเซอร์หยุดไหลตั้งแต่ตี 2 — ไม่มีใครรู้จนบ่ายวันถัดมา**
ตัวเฝ้าเครื่องหลัก (T1.285) จับเรื่องนี้ไม่ได้ เพราะเครื่องหลัก "ตอบ" อยู่ตามปกติ
มันแค่ไม่มีข้อมูลใหม่ให้คิด และ **หน้าจอยังขึ้นเลขเดิมค้างไว้เหมือนทุกอย่างปกติ**

#### จับสองอาการที่ต่างกัน

| อาการ | หน้าตา | สาเหตุที่เคยเจอ |
| --- | --- | --- |
| **ท่อหยุด** | ไม่มีค่าใหม่เข้ามาเกิน 30 นาที | เครื่องที่รันท่อหลับ · ท่อหลุด · ตู้ในฟาร์มดับ |
| **ท่อเดินแต่ของเสีย** | ค่ามาตรงเวลาแต่อุณหภูมิ/ความชื้นเป็น 0 ทั้งหมด | อุปกรณ์อ่าน RS485 ไม่ได้ |

อาการที่สองอันตรายกว่า เพราะ "มีข้อมูลเข้า" ทำให้ทุกตัวนับว่าปกติ
สะพานทิ้งค่าพวกนี้อยู่แล้ว (`ทิ้งค่าที่เป็นไปไม่ได้` ใน log) แต่เดิมไม่เคยบอกใครนอกจาก log

#### กฎเดียวกับตัวเฝ้าเครื่องหลัก

**ห้ามแตะฐานข้อมูล** (มีเทสต์คุม) — 28–29 ก.ย. กล่องดับกับข้อมูลหยุดไหล **เกิดพร้อมกัน**
ตัวเฝ้าที่พึ่งฐานจะเงียบในวันที่ต้องพูดที่สุด · อ่านจากต้นทางอย่างเดียว เก็บสถานะเป็นไฟล์

**ต่อต้นทางไม่ได้ ≠ ข้อมูลหยุดไหล** — กรณีนั้นข้ามรอบและเขียน log ไว้
ไม่ส่งไลน์ เพราะข้อความจะพาคนไปแก้ผิดเครื่อง (ไปไล่ที่ตัวส่ง ทั้งที่ตัวรับล่ม)

#### สองตัวเฝ้ากันไขว้

ตัวเฝ้าข้อมูลรันบนเครื่องผู้พัฒนา (เครื่องที่อ่านต้นทางได้) · ตัวเฝ้าเครื่องหลักก็รันบนเครื่องผู้พัฒนาเฝ้ากล่อง
ถ้า**เครื่องผู้พัฒนาหลับทั้งเครื่อง** ตัวเฝ้าข้อมูลก็หลับด้วย — ตัวที่จะดังแทนคือฝั่งกล่องที่เห็นว่าไม่มีการซิงก์เข้ามา
รูที่ยังเหลือคือ "ดับพร้อมกันทั้งสองเครื่อง" ซึ่งอย่างน้อยฝั่งใดฝั่งหนึ่งจะดังก่อนเสมอ

| ตัวแปร | ค่าตั้งต้น | หมายเหตุ |
| --- | --- | --- |
| `FLOW_MAX_AGE_MIN` | `30` | ค่าล่าสุดเก่ากว่านี้ = ท่อหยุด (เซนเซอร์ส่งทุก ~10 วินาที) |
| `FLOW_CHECK_MIN` | `5` | ตรวจทุกกี่นาที · พลาดติดกัน 3 ครั้งถึงส่ง |
| `FLOW_REMIND_MIN` | `1440` | เตือนซ้ำทุกกี่นาทีเมื่อยังไม่กลับมา |
| `FLOW_WATCH_NOTIFY` | `0` = ยังไม่ส่งจริง | **สวิตช์ของตัวเอง ไม่ใช่ `LINE_NOTIFY`** |

#### เปิดส่งจริง

```bash
# ใน .env ของเครื่องที่รันสะพานบทบาท sync (วันนี้คือเครื่องผู้พัฒนา)
FLOW_WATCH_NOTIFY=1
docker compose up -d bridge
```

#### ★★ สาเหตุที่พบบ่อยที่สุดคือ "เครื่องหลับ" และมันไม่ทิ้ง error ไว้เลย (ไล่จบ 5 พ.ย. 2569)

เครื่องผู้พัฒนาตั้งไว้ว่า **ใช้แบตแล้วหลับหลังว่าง 1 นาที · เสียบไฟแล้วไม่หลับเลย**
(`Battery Power: sleep 1` · `AC Power: sleep 0`) ตอนหลับเครื่องตื่นแค่ 45 วินาทีทุก ~15 นาที
ท่อจึงรับค่าได้แค่ช่วงนั้น และต้นทาง**ไม่เก็บย้อนหลังให้ ที่ขาดไปกู้ไม่ได้**

ผลที่วัดได้จริงจาก `sensor_reading` คืนวันที่ 3–5 พ.ย. 2569

| ช่วงเวลาไทย | แถว/ชม. | เครื่อง |
| --- | --- | --- |
| 13:00–18:00 | 1,000–1,800 | ตื่น (คนใช้งานอยู่) |
| 19:00–12:00 | **40–65** | หลับ |

★ **อาการนี้ไม่มี error ให้เห็น** ทุกคอนเทนเนอร์ยัง `Up` · ท่อยังรัน ·
`launchd` ไม่ได้รีสตาร์ตอะไร · `health-check.sh` ข้อ 1–2 ขึ้น `[ ดี ]` หมด
**ตัวที่ฟ้องคือจำนวนแถวต่อชั่วโมง** ไม่ใช่ log

```bash
pmset -g batt | head -2                 # ใช้แบตหรือเสียบไฟอยู่
pmset -g custom | sed -n '/Battery/,/AC Power/p'   # ค่า sleep ของฝั่งแบต
pmset -g log | grep -E 'Sleep  |DarkWake' | tail -20
```

➜ `health-check.sh` ข้อ 6 ตรวจเรื่องนี้ให้แล้ว · **แก้คือเสียบสายชาร์จ**
อย่าเสนอย้ายท่อไปกล่อง — ติดกติกาข้อมูลขององค์กรด้านบน ไม่ใช่ติดเทคนิค

#### แยกให้ออกระหว่าง "เครื่องผู้พัฒนาหลับ" กับ "ตู้ที่ฟาร์มเงียบ"

ถ้าเครื่องตื่นอยู่แล้วยังไม่มีค่าใหม่ ให้ตรวจที่**ต้นทางของท่อ** ว่ามีค่าเข้ามาไหม
ถ้าต้นทางเงียบด้วย = ตัวส่งที่ฟาร์มหยุด ฝั่งระบบนี้ทำอะไรไม่ได้ **ต้องแจ้งทีมหน้างาน**
(เกิดจริง 5 พ.ย. 2569 02:12 — เฝ้าดู 200 วินาทีไม่มีค่าเข้ามาเลย)

★ และอ่าน log ของสะพานให้เป็น — `"อ่านมา":67` **ไม่ได้แปลว่ามีค่าใหม่ 67 ค่า**
มันอ่านซ้ำช่วงเดิมทุกรอบจาก high-water mark · ตัวที่บอกว่ามีของใหม่จริงคือ `"เขียนเซนเซอร์"`

#### ดิสก์ใกล้เต็มก็ทำให้ข้อมูลหยุดไหล — ตัวเฝ้าตัวเดียวกันดูให้ด้วย (T1.297)

28 ก.ย. 2569 ท่อขึ้น `Request timed out` ตอนดิสก์เครื่องผู้พัฒนาใกล้เต็ม
ถ้าตัวเฝ้ารายงานแค่ "ข้อมูลหยุดไหล ไปดูที่ท่อ" **คนจะไล่หาสาเหตุผิดทาง** ทั้งที่คำตอบคือลบไฟล์
จึงตรวจดิสก์**ก่อน**ดูอายุข้อมูลเสมอ และใช้ข้อความคนละชุด

| ตัวแปร | ค่าตั้งต้น | หมายเหตุ |
| --- | --- | --- |
| `FLOW_DISK_PATH` | `/hostdisk` | โฟลเดอร์ที่ผูกมาจากเครื่องจริง · ไม่ตั้ง = ข้ามการตรวจดิสก์ |
| `FLOW_MIN_DISK_PCT` | `5` | เหลือน้อยกว่านี้ (%) แล้วเตือน |

★ **สองกับดักที่เสียเวลาไปแล้ว ห้ามพลาดซ้ำ**

1. **ในคอนเทนเนอร์ `/` ไม่ใช่ดิสก์ของเครื่อง** — วัดจากตรงนั้นได้ "ว่าง 416 GB" ขณะที่เครื่องเหลือจริง 7.8 GB
   compose จึงผูก `./docs` เข้ามาที่ `/hostdisk` แบบอ่านอย่างเดียวไว้ให้วัดโดยเฉพาะ
2. **`statfs` คืน `bsize` ไม่ตรงกับบล็อกจริงบน mount แบบนี้** (คืน 1 MiB ทั้งที่จริง 4 KiB)
   คิดเป็นไบต์แล้วได้ "ว่าง 1,987 GB" → **ต้องคิดเป็นสัดส่วน `bavail / blocks`** ซึ่งไม่ขึ้นกับขนาดบล็อก

### ★ ส่งคำสั่งไปตู้ควบคุมโรงเรือน (T1.284)

**วันนี้คำสั่งยังไม่ถูกส่งออกไปไหน** `CONTROL_TRANSPORT` ตั้งต้นเป็น `hold` คือ
ตรวจครบทุกด่านแล้ว **เก็บเข้าคิวในตาราง `control_command`** เท่านั้น
เพราะระบบสภาพแวดล้อมเป็นของอีกฝ่าย และสิ่งที่ได้รับมาไม่มีช่องสั่งงานเลย
(หลักฐานเต็มอยู่ใน `docs/TASKS.md` หัวข้อ T1.284)

```bash
# ดูว่าคิวมีอะไรค้าง
psql "$DATABASE_URL" -c "select requested_at, device_id, action, status, gate_code
                           from control_command order by requested_at desc limit 20"
```

#### ต้องได้อะไรจากเจ้าของระบบก่อนถึงจะเปิดใช้ได้

| ต้องได้ | เอาไปใส่ที่ไหน |
| --- | --- |
| ที่อยู่ปลายทางของอุปกรณ์แต่ละตัว (topic หรือ path) | `control_device.remote_addr` |
| รูป payload ที่ตู้รับ | เขียนตัวส่งใน `server/src/control/transport.js` |
| ช่วงค่าที่ยอมรับ (Hz ต่ำสุด/สูงสุด) | `FAN_HZ` ใน `server/src/control/validate.js` |
| ช่องทางตอบกลับว่าตู้ทำตามแล้ว | ตัวที่เปลี่ยน `sent` → `confirmed` (ยังไม่มี) |
| บัญชี/กุญแจที่เขียนได้ | `.env` ฝั่งเซิร์ฟเวอร์ **ห้ามขึ้นต้นด้วย `VITE_`** |

**★ ห้ามเขียนตัวส่งของจริงโดยเดาเอาเองว่า topic หรือ payload หน้าตาแบบไหน**
เดาผิดแล้วโชคดีคือไม่มีอะไรเกิดขึ้น เดาผิดแล้วโชคร้ายคือพัดลมในโรงเรือนจริงหยุด

#### ★ ต้องเขียน topic ที่จะ publish ไว้ในโค้ดไหม — **ไม่ต้อง**

ทางที่เลือกไว้คือ `outbox` ซึ่ง **ฝั่งที่ดูแลท่อเป็นคนส่งคำสั่งออกเอง** (ผู้ใช้ตัดสิน 5 ต.ค. 2569)
รูปของคำสั่งที่ส่งออกจึงอยู่ฝั่งเขา ไม่ใช่ในโค้ดนี้ — เหตุผลสามข้อ

1. คำสั่งไม่ต้องวิ่งผ่านช่องทางสาธารณะ (ใครก็ปลอมคำสั่งเข้าช่องเดียวกันได้)
2. ฝั่งนั้นถือ credential ของฟาร์มอยู่แล้ว ไม่ต้องเอารหัสมาไว้อีกที่
3. ไม่ต้องเพิ่ม dependency ฝั่งระบบนี้

ฝั่งระบบนี้ทำแค่เปิดกล่องขาออกให้มาดึง

```bash
# 1) ตั้งสองค่านี้ใน .env แล้วรีสตาร์ต api
CONTROL_TRANSPORT=outbox
CONTROL_OUTBOX_TOKEN=$(openssl rand -hex 32)

# 2) ตรวจว่ากล่องขาออกเปิดแล้ว (ไม่มีกุญแจต้องได้ 503 · กุญแจผิดต้องได้ 401)
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/api/control/outbox
curl -s -H "x-outbox-token: $CONTROL_OUTBOX_TOKEN" localhost:3000/api/control/outbox
```

ฝั่งที่ดูแลท่อวนสองจังหวะ (ตั้งไว้ทุก 5 วินาที)

| จังหวะ | เรียก | ได้/ส่งอะไร |
| --- | --- | --- |
| ดึง | `GET /api/control/outbox?limit=10` + header `x-outbox-token` | `{id, barnKey, deviceKind, deviceId, remoteAddr, action, hz, requestedAt}` เก่าก่อนใหม่ |
| ส่งต่อ | ตัวส่งของฝั่งเขาเอง | **topic/payload เขียนตรงนี้** — `remoteAddr` คือที่อยู่ที่เจ้าของระบบให้มา (เป็น null ได้ แล้วแปลงจาก `deviceId` เอง) |
| รายงานผล | `POST /api/control/outbox/<id>/ack` | `{"ok":true}` หรือ `{"ok":false,"detail":"PLC ไม่ตอบ"}` — **ปิดได้ครั้งเดียว ซ้ำได้ 409** |

**★ ลำดับสำคัญ** — ดึงมาแล้วต้องส่งตามลำดับเวลา สั่ง "เปิด" แล้ว "ปิด" ถ้าสลับลำดับ
ผลลัพธ์กลับด้านและไม่มีใครรู้ว่าเกิดอะไรขึ้น (API เรียงให้แล้ว อย่าไปจัดใหม่ใน flow)

**★ `ok: true` แปลว่า "ออกจากมือฝั่งที่ส่งแล้ว" ไม่ใช่ "พัดลมหมุนแล้ว"** สถานะในฐาน
จึงเป็น `sent` ไม่ใช่ `confirmed` — ช่องทางที่ PLC ตอบกลับว่าทำตามแล้วยังไม่มี

**รายการสเปกที่ต้องขอจากทีม PLC 7 ข้อ** — `docs/ส่งมอบ/ฉบับใช้งาน/handover/04-รับของทีมอื่น.md` หัวข้อ 4.4
รวมไว้ครบว่าต้องขออะไรบ้าง (7 ข้อ) และฝั่งระบบนี้เตรียมอะไรไว้แล้ว ส่งให้เขาได้เลย
ข้อที่ขาดมากที่สุดคือ **ช่องทางที่ตู้ตอบกลับว่าทำตามแล้ว** — ไม่มีข้อนี้หน้าจอต้องเขียนว่า
"ไม่ทราบสถานะ" ตลอดไป และกติกาอย่าง "ห้ามปิดพัดลมตัวสุดท้าย" บังคับไม่ได้เลย

**ถ้าอยากให้ API เป็นคนส่งคำสั่งออกเอง** ตัวส่งนั้น **ยังไม่ได้เขียน**
ตอบ 501 ไว้โดยตั้งใจ ต้องได้รูปของคำสั่งและบัญชีที่ส่งได้จากเจ้าของระบบก่อน
แล้วเขียนที่ `server/src/control/transport.js` ที่เดียว

#### ด่านความปลอดภัยตัดสินจากอะไร

**ไม่ได้ตัดสินจากสถานะอุปกรณ์ เพราะระบบนี้ไม่มี** ตู้ไม่ได้ส่งกลับมาว่าพัดลมตัวไหนหมุนอยู่
ตัดสินจากสองค่าที่รู้จริงเท่านั้น: **อุณหภูมิล่าสุด** (`sensor_reading`) กับ
**เพดานที่ตกลงไว้** (`alert_rule` — กฎของโรงเรือนชนะกฎของฟาร์ม ชนะกฎรวม)

| สถานการณ์ | ผล |
| --- | --- |
| อุณหภูมิถึงเพดาน + สั่งลดความเย็น | **ห้าม** — ยืนยันแล้วก็ไม่ผ่าน |
| ห่างเพดานไม่ถึง 1.5 °C + สั่งลดความเย็น | ถามกลับ — ยืนยันแล้วผ่าน |
| ไม่รู้อุณหภูมิ (ไม่มีค่า หรือเก่าเกิน 15 นาที) | **ห้าม** ลดความเย็น · สั่ง `auto` ได้ |
| ปิดปั๊มน้ำดื่ม (`critical`) | ถามกลับทุกครั้ง ไม่ว่าอากาศจะเย็นแค่ไหน |
| โรงเรือนออฟไลน์ · สั่งเกิน 10 ครั้ง/นาที | ห้าม ทุกคำสั่งรวม `auto` |

**"ลดความเย็น" ดูจากธง `cooling` ของอุปกรณ์ ไม่ใช่จากชนิด** — ม่านน้ำ (P3) เป็นปั๊ม
แต่เป็นอุปกรณ์ทำความเย็น ปิดตอนอากาศร้อนอันตรายไม่ต่างจากปิดพัดลม
ส่วนปั๊มระบายน้ำ (P2) ไม่เกี่ยว จึงปิดได้ตามปกติ

#### คำสั่งที่ถูกปฏิเสธก็ถูกบันทึก

ตั้งใจให้เป็นอย่างนั้น — แถว `status = 'rejected'` บอกว่าเคยมีคนพยายามปิดพัดลมตอน 34 °C
ซึ่งมีค่ามากกว่าคำสั่งที่ผ่าน และเป็นข้อที่เจ้าของระบบจะถามก่อนให้สิทธิ์เขียน

สลับ · แล้วยิงดูว่าเว็บตอบ 200 และบันเดิลตรงกับที่ build ไว้

### ★★★ ทำไมต้องใช้สคริปต์ ห้ามพิมพ์ `mv` เอง (6 พ.ย. 2569 — เว็บล่มมาแล้ว)

คำสั่งเดิมคือ `mv dist dist-old-DATE && mv dist-new dist` ซึ่ง**พังเมื่อถูกกดซ้ำ**

```
ขั้นแรก  mv dist dist-old-DATE     สำเร็จ ← ย้ายของที่ใช้อยู่ออกไป
ขั้นสอง  mv dist-new dist          ล้ม    ← dist-new ถูกใช้ไปแล้วตั้งแต่รอบก่อน
ผล      เว็บไม่เหลือไฟล์ให้เสิร์ฟ → 404
```

และเพราะ `dist-old-DATE` มีอยู่แล้วจากรอบก่อน `mv` จึง**ไม่ได้เขียนทับ**
แต่ย้าย `dist` **เข้าไปซ้อนข้างใน** กลายเป็น `dist-old-DATE/dist`
ซึ่งหาไม่เจอถ้าไม่รู้ว่าเกิดอะไรขึ้น — กู้ด้วยการย้ายกลับ

```bash
ssh root@<ที่อยู่ของกล่อง> 'mv /home/dev/dist-old-DATE/dist /home/dev/dist'
```

สคริปต์กันทั้งสองเคสนี้: ไม่มี `dist-new` = ไม่ทำอะไรเลยและไม่ถือว่าผิดพลาด ·
ชื่อสำรองชนกันก็หาชื่อใหม่แทนการย้ายซ้อน
➜ ทุกเคสมีเทสต์คุมที่ `test/deploySwap.test.js` (รันกับโฟลเดอร์ชั่วคราว ไม่แตะเว็บจริง)

### ★★ กติกาเรื่อง "คำสั่งที่ใช้ไปแล้ว"

ข้อนี้เขียนไว้ตั้งแต่ 28 ต.ค. 2569 แล้วยังพลาดซ้ำในวันที่ 6 พ.ย. จึงย้ำอีกครั้ง

- **คำสั่งที่รันไปแล้ว ห้ามทิ้งค้างไว้ในข้อความให้กดซ้ำ** — คนกดเพราะเห็นมันอยู่ตรงนั้น
  ถ้าจะทิ้งไว้ ต้องเขียนกำกับว่า "รันไปแล้ว อย่ากดอีก"
- **คำสั่งทำลายต้องไม่อยู่ในที่ที่กดได้ง่ายกว่าที่ควร**
- ถ้าคำสั่งเดียวมีสองขั้นที่ขั้นแรกทำลายของเดิม **ให้ทำเป็นสคริปต์ที่ตรวจก่อนเสมอ**
  อย่าหวังว่าคนจะกดถูกจังหวะ

### 3. ตรวจว่าขึ้นจริง

`ops/deploy-swap.sh` ตรวจให้แล้วตอนจบ แต่ถ้าอยากดูเองอีกรอบ

```bash
curl -s https://mew.plotnexuslab.com/ | grep -oE 'main-[A-Za-z0-9_-]+\.js'
```

ต้องได้ชื่อเดียวกับที่ `dist/index.html` ในเครื่องอ้างถึง **แล้วเปิดหน้าจริงดูด้วยตาด้วย**
ชื่อไฟล์ตรงพิสูจน์แค่ว่าไฟล์ถูกวางแล้ว ไม่ได้พิสูจน์ว่าหน้าตาถูก

`index.html` ตั้ง `cache-control: no-store` ไว้ ผู้ใช้จึงได้ของใหม่ทันทีที่รีเฟรช
ไม่ต้องสั่งใครล้างแคช

### ★★ ถอยกลับเมื่อของใหม่มีปัญหา

ของเดิมยังอยู่ที่ `/home/dev/dist-old-DATE` **อย่าเพิ่งลบจนกว่าจะมั่นใจ** —
มันคือทางถอยทางเดียวที่ไม่ต้อง build ใหม่ กินแค่ 5 MB บนดิสก์ที่ว่างเป็นเทระไบต์

ถอยด้วยการสลับกลับ: ย้าย `dist` ปัจจุบันไปเก็บไว้ชื่ออื่นก่อน **แล้วค่อย**
ย้าย `dist-old-DATE` กลับมาเป็น `dist`

**`dist-old-*` บนกล่องคือทางถอย ไม่ใช่ขยะ** — แต่ละอันคือหน้าเว็บรุ่นก่อนหน้าหนึ่งรุ่น
อันละ ~5 MB บนดิสก์ที่ว่างเป็นเทระไบต์ **อย่าเพิ่งลบ** จนกว่าจะมั่นใจว่ารุ่นที่ใช้อยู่ดีแล้ว
ดูว่าอันไหนเป็นรุ่นไหนด้วยคำสั่งนี้

```bash
ssh root@<ที่อยู่ของกล่อง> 'for d in /home/dev/dist*; do printf "%-36s %s\n" "$d" "$(grep -oE "main-[A-Za-z0-9_-]+\.js" $d/index.html | head -1)"; done'
```

★★★ **ห้ามเขียนคำสั่งถอยเป็น `rm -rf dist && mv dist-old dist` ทิ้งไว้ให้กด**
28 ต.ค. 2569 เขียนคำสั่งแบบนั้นไว้ต่อท้ายบรรทัดที่บอกว่า deploy สำเร็จ
ผู้ใช้กดเพราะนึกว่าเป็นขั้นตอนถัดไป **ของใหม่ถูกลบและเว็บถอยกลับไปเป็นของเก่า**
โดยที่ไม่มีใครตั้งใจ — คำสั่งทำลายต้องไม่อยู่ในที่ที่กดได้ง่ายกว่าที่ควร

## 6. เจอปัญหาแล้วทำยังไง

### หน้าเว็บขึ้นแถบเหลือง "ต่อหลังบ้านไม่ได้ — แสดงเฉพาะข้อมูลตัวอย่าง"

`swine-api` ไม่ตอบ — แอปยังใช้ได้แต่ฟาร์มจริงจะหายไปจากรายการ

```bash
docker compose logs api --tail 30
```

### สะพานขึ้น `เขียนเซนเซอร์: 0` ทุกรอบ

ปกติแปลว่า **ไม่มีข้อมูลใหม่ที่ต้นทาง** — ไล่ตามข้อ 5 ก่อน
ถ้าต้นทางมีค่าใหม่แต่ยังเขียน 0 ให้ดูว่า `sensor_source_map` มีข้อมูลไหม (ลืมรัน seed):

```bash
docker compose exec db psql -U swine -d swinesync -c "select count(*) from sensor_source_map;"
```

### กราฟย้อนหลังว่างเปล่าทั้งที่มีข้อมูลดิบ

ชั้นสรุปยังไม่ได้สรุปข้อมูลเก่าที่เพิ่ง backfill เข้ามา — สั่งสรุปใหม่ทั้งหมด:

```bash
docker compose exec db psql -U swine -d swinesync -c "call refresh_continuous_aggregate('sensor_hourly', null, null);" -c "call refresh_continuous_aggregate('sensor_daily', null, null);"
```

> ต้องแยกเป็นสอง `-c` — ใส่สองคำสั่งใน `-c` เดียว psql จะห่อเป็น transaction
> แล้ว `refresh_continuous_aggregate()` รันในนั้นไม่ได้

### หน้าจอขึ้นเลข 0 แปลก ๆ (0 °C, NH₃ 0 ppm)

"ศูนย์ปลอม" จากยุคก่อนแก้ท่อหลุดเข้ามา — ล้างด้วยสคริปต์ที่เตรียมไว้ (รันซ้ำได้):

```bash
docker compose exec -T db psql -U swine -d swinesync -f - < server/src/db/cleanup-legacy-zeros.sql
```

### อยากล้างฐานเริ่มใหม่หมด

```bash
docker compose down -v && docker compose up -d --build
```

> ⚠️ `-v` **ลบข้อมูลในฐานทิ้งทั้งหมด** · ใช้ได้เฉพาะกับฐานสำเนาบนเครื่องที่ใช้พัฒนา
> **ห้ามใช้กับฐานของจริงบนกล่อง** ของที่ลบไปดึงย้อนหลังกลับมาไม่ได้ (และอย่าลืมรัน seed ใหม่)

## 7. สิ่งที่ต้องระวัง

⚠️ **ทุกเส้นทางที่อ่านข้อมูลต้องล็อกอินแล้ว** (T1.242, 14 ก.ย. 2569) — เหลือ `/api/health` กับ
`/api/auth/login` ที่เรียกได้โดยไม่มี token · ก่อนหน้านั้น `/farms` `/barns/*` `/alerts` `/assistant/now`
อ่านได้ทุกคน และหน้าเว็บพอร์ต 8080 เปิดรับทั้งวง Wi-Fi (`0.0.0.0`) คนในวงเดียวกันจึงดึงค่าฟาร์มได้
พอร์ต 8080 **ยังเปิดรับทั้งวงอยู่** (ตั้งใจ ให้เปิดดูจากมือถือได้) — ถ้าไม่ต้องการ ตั้ง `WEB_PORT=127.0.0.1:8080` ใน `.env`

⚠️ **การเก็บข้อมูลผูกกับเครื่องนี้** — ปิดเครื่องเมื่อไหร่ข้อมูลขาดช่วงทันที
ณ 24 ส.ค. 2026 ช่วงเวลา 47 วันมีข้อมูลจริงแค่ประมาณ 7 วัน
ถ้าจะใช้จริงต้องย้ายไปรันบนเครื่องที่เปิดตลอด

⚠️ **ท่อรับค่าเดินผ่านช่องทางสาธารณะ** — ใครก็อ่านค่าฟาร์มได้และปลอมค่าส่งเข้ามาได้ (งานของอีกทีม)

⚠️ **เซนเซอร์ที่ใช้ได้จริงมีแค่ 2 ตัว** — โซน B กับตัวนอกโรงเรือน
โซน A/C ส่งเลข 0 มาตลอด (อุปกรณ์เสีย) · NH₃ · CO₂ ไม่เคยส่งค่าจริงมาเลย
ส่วนกำลังไฟกับหน่วยสะสม **ส่งมาตลอด** แค่ท่อแมปผิดชื่อ (แก้แล้ว — ดูข้อ 10)
หน้าจอจึงขึ้นว่าออฟไลน์/ขีดกลาง ซึ่งถูกต้องแล้ว ไม่ใช่บั๊ก

## 9. หน้าตา API (เท่าที่มีตอนนี้)

ทุกเส้นทางขึ้นต้น `/api` · ตอบ JSON · **ต้องแนบ `Authorization: Bearer <token>`** (ยกเว้น `/health`)

เอา token มาใช้กับ curl ได้สองทาง

```bash
# 1) ล็อกอินจาก shell (ใส่รหัสของตัวเอง)
TOKEN=$(curl -s -X POST localhost:3000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"รหัสผ่าน"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
# 2) หรือคัดลอกจากเบราว์เซอร์ที่ล็อกอินอยู่: DevTools → Console → localStorage.getItem("swine-sync:token")
```

ไม่แนบ = ได้ `401 ต้องเข้าสู่ระบบก่อน`

| Method | Path | ได้อะไร |
|---|---|---|
| GET | `/health` | สถานะ + จำนวนแถว + เวลาที่วัดล่าสุด |
| GET | `/farms` | รายการฟาร์ม + ตัวเลขสรุป |
| GET | `/farms/:id/barns` | โรงเรือน + ค่าล่าสุด (แยกในโรงเรือน / นอกโรงเรือน) |
| GET | `/barns/:id/readings/latest` | ค่าล่าสุดทุก metric |
| GET | `/barns/:id/readings?range=24h&metrics=temp_c,humidity` | ชุดเวลา (`≤48h` รายชั่วโมง · ยาวกว่านั้นรายวัน) |
| GET | `/barns/:id/sensor-map` | ค่าล่าสุดแยกตามโซน A–D |
| GET | `/barns/:id/twin` | แบบจำลองโรงเรือน: แบบจำลอง · ความแม่น · ของจริงเทียบที่คาด · สุขภาพเซนเซอร์นอกเล้า |
| GET | `/barns/:id/twin/scenario` | วัตถุดิบจำลองสถานการณ์: พารามิเตอร์ · จุดเริ่ม · แดด 24 ชม. ข้างหน้า · วันที่ร้อนที่สุด |
| GET | `/barns/:id/shift-report?from=&to=` | รายงานส่งเวร: ค่าในเล้า · ความครบของข้อมูล · เหตุในกะ · งานค้าง · ไฟ · ใบรับเวร (ช่วงยาวสุด 7 วัน) |
| POST | `/barns/:id/shift-report/handover` | รับเวร `{from, to, note}` — **ผู้บันทึกขึ้นไป** · ครั้งเดียวต่อกะ (ซ้ำได้ 409) · กะยังไม่จบได้ 400 |
| GET | `/barn-logs/:barnKey` | บันทึกของคนในโรงเรือน (หมูตาย · ป่วย · ย้าย · ให้อาหาร · ให้ยา) — `barnKey` เป็นรหัสแบบหน้าเว็บ เช่น `F-KPP-A1` |
| POST · PATCH · DELETE | `/barn-logs/:barnKey[/:id]` | เพิ่ม · แก้ · ลบแบบซ่อน — **ผู้บันทึกขึ้นไป** · เวลาเข้า-ออกเป็นเวลาไทยไม่มีโซน |
| POST | `/barn-logs/:barnKey/import` | ย้ายบันทึกเก่าในเครื่องขึ้นฐาน `{entries}` — ส่งซ้ำไม่ได้แถวซ้ำ (`client_id`) |

### บั๊กที่เจอเพราะต่อของจริง (mock ไม่มีวันโผล่ให้เห็น)

1. **ต้นทางตอบ CSV แบบ CRLF** — ไม่ตัด `\r` ทิ้ง ชื่อ field คอลัมน์สุดท้ายกลายเป็น `"current_a\r"`
   หา mapping ไม่เจอ → **เขียนได้ 0 แถวโดยไม่มี error สักตัว** (log บอกว่าอ่านมา 353,918 แต่เขียน 0)
2. **`null` โผล่บนหน้าจอ** — `` `${f.id} · ${f.district} · ${f.province}` `` กลายเป็น `"F-KPP · null · กำแพงเพชร"`
   ข้อมูลจริงมีไม่ครบเสมอ ต่อจุดคั่นต้องใช้ `.filter(Boolean).join(" · ")` ทุกครั้ง

### บั๊กรอบสาม — กำลังไฟกับหน่วยไฟไม่ขึ้นแดชบอร์ด (แก้แล้ว 27 ส.ค. 2026)

**สองเรื่องซ้อนกัน**

**1. ท่อมองหาชื่อค่าผิด** — มิเตอร์ส่ง `PW` (กำลังไฟ kW) กับ `EN` (หน่วยสะสม kWh)
แต่ฝั่งรับมองหา `Power`/`P` และ `KWH`/`kwh` ค่าจึงหล่นหายตั้งแต่ต้นทาง ไม่เคยถึงฐานสักครั้ง
เห็นได้เฉพาะตอนไปดูค่าดิบที่ต้นทาง — ฝั่งระบบนี้เห็นแค่ "ไม่มีค่า" เลยสรุปผิดว่ามิเตอร์ไม่ส่ง

### ตัวประกอบกำลัง (cos φ) — เอาช่องออกจากการ์ดแล้ว (T1.154)

**cos φ คืออะไร** ไฟฟ้ากระแสสลับมีกำลังสองแบบ — กำลังที่ทำงานจริง (kW) กับกำลังที่ไหลไป-กลับ
ในสายโดยไม่ได้ทำงาน (kVAR) ตัวประกอบกำลังคือสัดส่วน kW ÷ kVA อยู่ระหว่าง 0–1
ยิ่งใกล้ 1 ยิ่งใช้ไฟคุ้ม มอเตอร์กับพัดลมจะดึงค่านี้ให้ต่ำลง โรงงานที่ค่านี้ต่ำมาก
การไฟฟ้าคิดค่าปรับได้ — จึงเป็นตัวเลขที่มีความหมายจริงถ้าวัดได้

**ทำไมเอาออก** เพราะ**วัดไม่ได้** — ไม่ใช่เพราะไม่สำคัญ

| ที่มา | ตรวจแล้วเจออะไร |
|---|---|
| ค่าที่ท่อส่งมา | มีตัวแปร `power_factor` จริง ส่งมาทุก 30 วินาที |
| ค่าที่ส่งมา | **9,618 จุดใน 3 วัน เป็น 0 ทั้งหมด** (min = 0, max = 0) |
| ค่าจำลอง (mock) | เลขสุ่ม 0.88–0.95 ไม่ใช่ค่าที่วัดจากอะไรเลย |

ตรวจซ้ำเองได้ตลอดจากค่าในฐาน — ถ้าวันหนึ่งค่าสูงสุดไม่เป็น 0 แล้ว แปลว่ามิเตอร์เริ่มวัดจริง ค่อยเอาช่องกลับมา

**0 ตรงนี้แปลว่า "ไม่ได้วัด" ไม่ใช่ "วัดได้ศูนย์"** — ยืนยันด้วยเลขอื่นในมิเตอร์เดียวกัน
3 × 225 V × 5.7 A ≈ 3.85 kVA เทียบกับ PW 3.4 kW → cos φ จริงราว 0.88
ถ้าเป็น 0 จริงตามที่ส่งมา มิเตอร์จะต้องอ่านกำลังไฟได้ 0 kW ด้วย ซึ่งไม่ใช่

**แก้ที่ไหน**

| ไฟล์ | แก้อะไร |
|---|---|
| `ElectricalPanel.jsx` | ลบแผ่นค่า cos φ · คำอธิบายใต้ "กำลังไฟ" เลิกอ้างคำที่ไม่มีบนจอแล้ว |
| `LiveFarmsProvider.jsx` | เลิกยัด `"ตัวประกอบกำลัง"` ลง `missing` และเลิกส่ง `powerFactor` |
| `i18n/en.js` · `zh.js` | ลบคีย์ `ตัวประกอบกำลัง` · เพิ่มคำแปลคำอธิบายใหม่ |

**`barnSystems.js` ไม่แตะ** — ค่าจำลองยังคำนวณ kW จาก PF อยู่ข้างใน (V × A × PF ÷ 1000)
เป็นการคำนวณภายใน ไม่ได้ขึ้นจอ และกติกาห้ามแก้โครงสร้าง mock data

### หน้าเว็บมีของจริงเสิร์ฟแล้ว — ไม่ต้องพึ่ง `npm run dev`

บริการ `web` ใน compose เสิร์ฟไฟล์ที่ build แล้วที่ **พอร์ต 8080** และส่งต่อ `/api` ไปหลังบ้านให้เอง

```bash
npm run build && docker compose up -d --build web
```

**ต้อง `npm run build` บนเครื่องก่อนเสมอ** เพราะเครือข่าย CPF ทำ TLS interception
(ใบรับรองที่ตอบกลับมาเป็นของ `*.cpf.co.th`) Docker จึงดึง image ใหม่จาก Docker Hub ไม่ได้เลย

```
failed to verify certificate: x509: certificate is valid for *.cpf.co.th, cpf.co.th, not auth.docker.io
```

ด้วยเหตุนี้ `web/Dockerfile` จึงใช้ `node:22-alpine` ที่มีอยู่ในเครื่องแล้ว **ไม่ใช่ nginx**
และตัวเสิร์ฟเป็น `web/server.js` ที่เขียนด้วยของที่มากับ Node ล้วน ไม่มี dependency
(ถ้าวันหนึ่งดึง image ได้ ให้สลับไปใช้ `web/nginx.conf` ที่เตรียมไว้เทียบเท่ากันแล้ว)

**ที่ต้องระวังในตัวเสิร์ฟ** — `up.pipe(res)` ห้ามเปลี่ยนเป็นการอ่านให้ครบก่อนส่ง
เพราะผู้ช่วย AI ตอบเป็นสายทีละคำ (NDJSON) ถ้าอมไว้จนจบ ผู้ใช้จะเห็นจอนิ่งเป็นนาที
ตรวจแล้วผ่าน: หน้าเว็บขึ้น "AI กำลังคิด…" → นับ 6 วิ / 12 วิ → ตัวอักษรเริ่มไหลที่วินาทีที่ 21

ผูกกับรอบซิงก์เพราะสองอย่างนี้ต้องเดินคู่กัน และรอบซิงก์เดินทุก 30 วินาทีไม่ว่าจะมีค่าใหม่หรือไม่

**เกณฑ์ตั้งต้น** (migration `1756040400000_default-alert-rules`) ต้องตรงกับค่าตั้งต้นฝั่งหน้าเว็บเสมอ

| `nh3` | เกิน 15 ppm | ต้องจัดการ | 5 นาที |


**เรื่องที่ต้องรู้**

- ฐาน **ไม่เก็บข้อความไทย** เก็บแค่ `code` + `params` แล้วหน้าจอแต่งประโยคเองที่
  `src/lib/api/alertText.js` — ถ้าเก็บข้อความสำเร็จรูป วันที่สลับเป็น en/zh

- ยังไม่มีปุ่ม "รับทราบ" บนหน้าจอ (ตาราง `alert` รองรับแล้ว รอ auth ก่อนถึงจะรู้ว่าใครกด)

### เกณฑ์ในหน้าตั้งค่า ↔ เกณฑ์ที่หลังบ้านใช้จริง (T1.144)

ผูกกันแล้วผ่าน `src/lib/settings/useAlertRuleSync.js` — **หลังบ้านเป็นตัวจริง**
เพราะเกณฑ์ระดับระบบเป็นของที่ทุกคนในเครือใช้ร่วมกัน ไม่ใช่ความชอบของเครื่องใดเครื่องหนึ่ง

- **เปิดแอป** → ดึงจาก `GET /api/alerts/rules` มาทับค่าในเครื่อง ทุกเครื่องจึงเห็นตรงกัน
- **แก้ในหน้าตั้งค่า** → หน่วง 0.8 วินาทีแล้วส่งขึ้น `PUT /api/alerts/rules`

⚠️ `PUT /api/alerts/rules` เป็น **เส้นทางเขียนเส้นทางแรกของทั้ง API และยังไม่มี auth**

## พอร์ตของ dev server — 5173 ตายตัว

`npm run dev` เปิดที่ **http://localhost:5173** เสมอ ไม่มีวันเลื่อนไปพอร์ตอื่นเอง

ตั้งไว้สองที่ ต้องตรงกันทั้งคู่

| ไฟล์ | ค่า | หน้าที่ |
|---|---|---|
| `vite.config.js` | `host: "127.0.0.1"` | ผูกกับ IPv4 — ค่าตั้งต้น (`localhost`) กลายเป็น IPv6 อย่างเดียวบนเครื่องนี้ แล้วเบราว์เซอร์ต่อไม่ติด |
| `vite.config.js` | `strictPort: true` | พอร์ตไม่ว่าง = พังตั้งแต่สตาร์ท ไม่ใช่เลื่อนไปพอร์ตอื่นเงียบ ๆ |
| `.claude/launch.json` | `"autoPort": false` | กันเครื่องมือ preview จัดพอร์ตใหม่ให้ |

**ถ้าขึ้น `Error: Port 5173 is already in use`** แปลว่ามี dev server ค้างอยู่ (เคยเจอตัวที่ค้างมา 9 วัน)
ตัวที่รันอยู่เดิมยังใช้งานได้ตามปกติ — ตัวใหม่แค่ไม่สตาร์ท ไม่มีอะไรพัง

ดูว่าใครยึดอยู่

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
```

ปิดทิ้งแล้วเปิดใหม่

```bash
kill $(lsof -ti tcp:5173) && npm run dev
```

**ทำไมถึงเลือกให้พังดีกว่าเลื่อนพอร์ต** เลื่อนพอร์ตอัตโนมัติทำให้ลิงก์ที่เปิดค้างไว้ตายเงียบ ๆ
แล้วต้องไล่หาพอร์ตใหม่ทุกครั้ง ส่วนข้อมูลใน localStorage ผูกกับพอร์ต — เปลี่ยนพอร์ตทีคือ
บัญชีที่จดจำไว้ เลย์เอาต์ที่จัดเอง และบันทึกในโรงเรือน หายหมดเหมือนเครื่องใหม่

| ตัวแปร | คืออะไร |
| --- | --- |
| `CPF_AI_API_KEY` | กุญแจที่อีกทีมออกให้ (ขึ้นต้น `cpfai_`) |

| `CPF_AI_LEVEL` | ระดับคำตอบที่กุญแจนี้ขอได้ (ดูจาก `max_level` ที่ `/whoami` ตอบ) |

### เรื่องที่ต้องรู้ก่อนไปแก้

**คำตอบมาสองแบบ และช้าคนละโลก** ถามค่าเซนเซอร์ตรง ๆ ("วันนี้ฝนตกไหม") ตอบใน ~0.5 วินาที
แต่คำถามที่ต้องให้โมเดลสรุป ใช้เวลา **20 วินาที ถึงเกิน 3 นาที** ถ้ามีคนใช้พร้อมกันจนเข้าคิว
ห้องแชทจึงต้องขึ้นตัวนับเวลาไว้ตลอด และมีปุ่มหยุด

**นับเวลาแบบ "เงียบไปนานแค่ไหน" ไม่ใช่ "ทั้งหมดกี่นาที"** เคยตั้งเพดานรวมไว้ 3 นาที
แล้วคำตอบที่กำลังจะมาถึงโดนตัดทิ้งเพราะติดคิว — ระหว่างรอ AI ส่งสัญญาณ `{"waiting":N}`
มาทุก ~6 วินาทีอยู่แล้ว "เงียบไปหนึ่งนาทีเต็ม" ต่างหากที่แปลว่าตายจริง

**`thinking` ไม่ใช่คำตอบ** ในสตรีมมีทั้ง `content` (คำตอบจริง) และ `thinking`
(ความคิดภายในของโมเดล เป็นภาษาอังกฤษดิบ ยาวกว่าคำตอบหลายเท่า และเดาผิดระหว่างทางบ่อย)
เอา `thinking` ไปแสดงเป็นคำตอบไม่ได้ ใช้ได้แค่เป็นสัญญาณว่ายังทำงานอยู่

**ต่อ AI ไม่ได้ = ตกกลับไปใช้ `answers.js` ในเครื่อง ไม่ใช่ขึ้น error**
แล้ว **ทุกฟองต้องติดป้ายว่าคำตอบมาจากไหน** — ตัวเลขจากเซนเซอร์จริงกับตัวเลขตัวอย่าง
เอาไปตัดสินใจต่อคนละเรื่องกันเลย ถ้าไม่บอก คนจะเอาตัวเลขสมมติไปสั่งเปิดพัดลมจริง

**บริบทที่ส่งไปให้ AI ไม่รวมคำตอบจาก `answers.js`** ถ้าปนเข้าไป AI จะรับตัวเลขจาก
mock data มาเป็นข้อเท็จจริง แล้วตอบต่อจากตัวเลขที่ไม่มีอยู่จริง

### ⚠️ ยังค้างอยู่ — ต้องทำตอนทำ `/auth` เสร็จ

AI ฝั่งโน้นรู้จักผู้ใช้จากหัวข้อ `X-CPF-User-ID` และ **รับเฉพาะชื่อที่ลงทะเบียนกับเขาไว้แล้ว**
(ลองส่ง `admin` ของระบบนี้ไปตรง ๆ → ตอบ 401) ตอนนี้จึงต้องแปลงผ่าน `CPF_AI_USER_MAP`

แต่เรื่องที่ใหญ่กว่าคือ **หลังบ้านของระบบนี้ยังไม่มีระบบยืนยันตัวตน** ชื่อผู้ใช้ที่ห้องแชทส่งมา
จึงยังเชื่อไม่ได้จริง ใครยิงตรงเข้าพอร์ต 3000 ก็อ้างเป็นใครก็ได้ (ดูที่ทำเครื่องหมาย `TODO(auth)`
ไว้ใน `server/src/modules/assistant/route.js`)

➜ **ห้ามเปิดพอร์ต 3000 ออกนอกวงแลนจนกว่าจะทำ `/auth` เสร็จ** — ข้อห้ามเดิมข้อเดียวกับ
`PUT /api/alerts/rules` แต่ตอนนี้หนักขึ้น เพราะเส้นทางนี้ใช้โควตา AI ของทีมอื่นได้ด้วย

### AI ตัวนี้ทำอะไรได้บ้าง (ทดสอบแล้ว 26 ส.ค. 2569)

| ถามอะไร | ได้จากไหน | เร็วแค่ไหน |
| --- | --- | --- |
| ค่าเซนเซอร์ตอนนี้ ("วันนี้ฝนตกไหม") | เซนเซอร์จริง 2 จุดที่กำแพงเพชร | ~0.5 วิ |
| พยากรณ์อากาศล่วงหน้า | บริการพยากรณ์ข้างนอก | ผ่านโมเดล |
| ราคาหมู ราคาทอง ข่าวโรคระบาด | **ค้นเว็บสด** | ผ่านโมเดล |
| ความรู้ทั่วไป | ความรู้ในตัวโมเดล | ผ่านโมเดล |

**มันค้นเว็บได้ และค้นได้ทุกเรื่อง ไม่จำกัดแค่เรื่องหมู** (ลองถามราคาทองก็ตอบพร้อมอ้าง
ประกาศสมาคมค้าทองคำ) และมันบอกเองด้วยว่าค้นไม่เจออะไรบ้าง

⚠️ **คำตอบที่มาจากการค้นเว็บ อ้างคนละแหล่งได้คนละตัวเลข** — ถามราคาหมูสองครั้งได้
74–78 บาท (อ้างสมาคมผู้เลี้ยงสุกรฯ) กับ 70 บาท (อ้าง สศก. ผ่านราคาเกษตรไทย)
ไม่ใช่ว่าอันไหนผิด แต่คนละแหล่งคนละเกณฑ์ ➜ เอาไปใช้ตัดสินใจเรื่องเงินต้องเช็กแหล่งเองก่อน

### ทางถอยตอน AI ตอบไม่ได้ — ค้นเว็บให้แทน (T1.150)

เดิม AI ล่มแล้วผู้ช่วยตกไปตอบจาก mock data อย่างเดียว ซึ่งช่วยอะไรไม่ได้เลยกับคำถาม
อย่าง "ราคาหมูวันนี้เท่าไร" ตอนนี้มีทางถอยเป็นการค้นเว็บ

**ทางเดินตอน AI ใช้ไม่ได้** (`fallbackAnswer` ใน `Assistant.jsx`)

| คำถามเข้าเรื่องอะไร | ทำอะไร |
| --- | --- |
| `alerts` `offline` `help` `farms` | ตอบจากในเครื่องอย่างเดียว |
| เรื่องอื่นในแดชบอร์ด | ตอบจากในเครื่อง **แล้วค้นเว็บมาเสริม** |
| ไม่เข้าเรื่องไหนเลย | ค้นเว็บอย่างเดียว |
| ค้นเว็บก็ไม่ได้ | ตกกลับมาที่ข้อมูลในเครื่อง |

**ทำไมกลุ่มกลางต้องให้ทั้งสองอย่าง** เพราะคำที่ `answers.js` ใช้จับเรื่องกว้างเกินจะเชื่อได้ —
เรื่อง `finance` มีคำว่า "ราคาหมู" อยู่ในรายการ ทั้งที่มันตอบเรื่องกำไรขาดทุนของฟาร์มที่ดูแลอยู่
พอถาม "ราคาสุกรมีชีวิตวันนี้กิโลละเท่าไร" ระบบเลยตอบงบการเงินกลับไปแล้วไม่ยอมค้นเว็บ
เพราะคิดว่าตอบได้แล้ว ➜ ให้ทั้งสองอย่างแล้วผู้ใช้เลือกเอง ดีกว่าเดาผิดแล้วปิดอีกทางทิ้ง

**ยังมีอีกทางหนึ่ง**: AI ตอบกลับมาแล้วแต่เนื้อความแปลว่า "ไม่รู้" (`soundsUnanswered`)
จะค้นเว็บมาต่อท้าย **โดยไม่ลบคำตอบของ AI ทิ้ง** เพราะบ่อยครั้งมันบอกด้วยว่าไม่รู้เพราะอะไร
(เช่น "เล้า R ไม่มีเซนเซอร์วัดฝุ่น") ซึ่งมีประโยชน์กว่าผลค้นดิบ ๆ
รายการวลีที่ใช้จับ **ตั้งใจให้แคบ** — จับกว้างแล้วคำตอบดี ๆ ที่มีคำว่า "ไม่พบฝนล่าสุด"
จะโดนตัดสินว่าเป็นคำตอบเสีย แล้วเอาผลค้นไปแปะรบกวนเปล่า ๆ

### ตัวค้นเว็บ (`server/src/modules/assistant/search.js`)

ใช้หน้า html ของ DuckDuckGo **ไม่ต้องสมัครกุญแจ** ใช้ได้ทันที

⚠️ **มันคือการอ่านหน้าเว็บ ไม่ใช่ API ที่เขารับประกัน** เขาเปลี่ยนหน้าเมื่อไรก็พังเมื่อนั้น
อาการเวลาพังคือ `results: []` เงียบ ๆ (ไม่ error) แล้วผู้ช่วยจะตกกลับไปใช้ข้อมูลในเครื่อง
ตรวจด้วย

```bash
curl -s -X POST localhost:3000/api/assistant/search -H "Content-Type: application/json" -d '{"q":"ราคาหมูวันนี้"}'
```

ได้อาร์เรย์ว่างทั้งที่เน็ตปกติ = ถึงเวลาย้ายไปใช้เจ้าที่มีกุญแจ (Brave Search / Tavily มีโควตาฟรี)
แก้แค่ฟังก์ชัน `webSearch` ตัวเดียว ที่เหลือไม่ต้องแตะ

**สองอย่างที่ทำไว้แล้วและห้ามเอาออก**
- ทิ้งลิงก์ที่ไม่ใช่ `http`/`https` — กัน `javascript:` หลุดไปเป็น `<a href>` บนหน้าเว็บ
- ทิ้งผลที่ยังชี้กลับไปที่ duckduckgo.com — พวกนั้นคือโฆษณา (เคยเจอถามราคาหมู
  แล้วผลแรกเป็นโฆษณาร้านวัสดุก่อสร้าง)

**ผลค้นคือข้อความจากคนแปลกหน้า** หน้าเว็บจึงแสดงเป็นข้อความล้วนพร้อมชื่อเว็บกำกับ
ติดป้าย "ผลค้นจากเว็บ ยังไม่มีใครตรวจให้" และเปิดแท็บใหม่เสมอ — **ห้ามทำให้หน้าตา
เหมือนคำตอบของผู้ช่วย** ไม่งั้นผู้ใช้จะอ่านหัวข้อของเว็บแปลกหน้าเป็นคำตอบไปเลย

⚠️ `POST /api/assistant/search` เป็นอีกเส้นทางที่ยังไม่มี auth และมันยิงออกเน็ตแทนคนเรียก
ใครเข้าถึงพอร์ต 3000 ได้ก็ใช้เครื่องนี้เป็นตัวค้นแทนตัวเองได้ — เหตุผลเพิ่มอีกข้อที่
**ห้ามเปิดพอร์ต 3000 ออกนอกวงแลน**

### อากาศของจังหวัดอื่น — ไม่ผ่าน AI (T1.151)

**AI ตอบเรื่องนี้ไม่ได้** ทดสอบแล้วเจอชัด: ถาม "อุณหภูมิที่เชียงใหม่ตอนนี้เท่าไร"
ตัวจัดเส้นทางของมันดักคำว่า "อุณหภูมิ" แล้วย้อนถามว่า *"ต้องการดูอุณหภูมิที่จุดใดครับ
1. กำแพงเพชร สำนักงาน 2. กำแพงเพชร เล้า R 5/2"* — มองข้ามคำว่าเชียงใหม่ไปทั้งคำ
ใส่คำสั่งกำกับนำหน้า ("ไม่ต้องดูเซนเซอร์…") ก็ยังโดนดักเหมือนเดิม

เลี่ยงคำว่า "อุณหภูมิ" ถึงจะหลุดไปที่โมเดล แต่คำตอบไม่แน่นอน — เชียงใหม่มันค้นเน็ตให้
ส่วนขอนแก่นมันตอบว่า *"ไม่มีสิทธิ์อ่านข้อมูลขอนแก่น"*

➜ **เรื่องนี้มีคำตอบที่ถูกต้องแน่นอนอยู่แล้ว ไม่ต้องให้ใครเดา** ยิงถาม Open-Meteo ตรง ๆ
(ฟรี ไม่ต้องมีกุญแจ เป็น API จริงที่เขาประกาศไว้ ไม่ใช่การอ่านหน้าเว็บแบบ `search.js`)
ได้ตัวเลขจริงทุกครั้ง เร็วกว่า ไม่กินโควตา AI ของอีกทีม และ **ใช้ได้แม้ตอน AI ล่ม**

**เงื่อนไขที่จะเข้าทางนี้ ต้องครบทั้งสองข้อ** (`src/lib/api/thaiPlaces.js`)
1. มีคำเกี่ยวกับอากาศ — ไม่งั้น "โรคระบาดที่เชียงใหม่" จะถูกลากไปตอบเรื่องอากาศ
2. มีชื่อสถานที่ที่ **ไม่ใช่** ที่ตั้งเซนเซอร์ของโครงการนี้ — ถ้าเป็นกำแพงเพชรต้องปล่อยให้ AI
   อ่านค่าจากเซนเซอร์จริง ซึ่งแม่นกว่าค่าพยากรณ์ของทั้งจังหวัด
   (เช็กจาก `sources` ที่ `/status` ส่งมา — เพิ่มจุดวัดใหม่แล้วกฎนี้ตามเองอัตโนมัติ)

**ชื่อสั้น ๆ ต้องมีคำนำหน้าบอกว่าเป็นสถานที่** ("จังหวัด" "จ." "ที่" "อำเภอ" …)
ไม่มีข้อนี้จะพังทันทีในแดชบอร์ดหมู เพราะภาษาไทยเขียนติดกัน:

| ชื่อ | ไปพ้องกับ |
| --- | --- |
| แพร่ | โรค**แพร่**ระบาด |
| เลย | บอก**เลย** ได้**เลย** |
| ตาก | **ตาก**แดด **ตาก**อากาศ |

ใช้เกณฑ์ "ยาวไม่เกิน 4 ตัวอักษร ต้องมีคำนำหน้า" ครอบคลุมทั้งหมดโดยไม่ต้องไล่เขียนทีละคำ

**ตรวจ**

```bash
curl -s -X POST localhost:3000/api/assistant/weather -H "Content-Type: application/json" -d '{"place":"เชียงใหม่"}'
```

**สรุปว่าคำถามไหนไปทางไหน**

| ถามอะไร | ใครตอบ |
| --- | --- |
| "อุณหภูมิในเล้า R" | AI → เซนเซอร์จริง |
| "อากาศที่กำแพงเพชร" | AI → เซนเซอร์ + พยากรณ์ของมันเอง |
| "อุณหภูมิที่เชียงใหม่" | Open-Meteo (AI ตอบไม่ได้) |
| "โรคสุกรที่ควรระวัง" | AI → ค้นเว็บเอง แล้วโยงกับค่าเซนเซอร์จริงของฟาร์มให้ด้วย |
| AI ล่ม + เรื่องนอกฟาร์ม | ค้นเว็บ → ลิงก์ |

### ค่าเซนเซอร์ "ตอนนี้" ไม่ต้องถาม AI (T1.152)

**AI ช้ามากกับคำถามง่ายที่สุด** วัดจริง: ถาม "ตอนนี้กี่องศา" ใช้ **28–150 วินาที**
ทุกคำถามเรื่องเซนเซอร์ถูกส่งเข้าโมเดลหมด ไม่มีทางลัด และเข้าคิวรวมกับคนอื่นด้วย
(ลองระบุชื่อจุดไปตั้งแต่แรกเพื่อเลี่ยงการย้อนถาม — วัดแล้วก็ยังช้าเท่าเดิม 78–150 วินาที)

แต่ **ค่าชุดเดียวกันอยู่ในฐานข้อมูลของระบบนี้อยู่แล้ว** สะพานดึงเข้ามาทุก 30 วินาที
`GET /api/assistant/now` อ่านจากตรงนั้น — วัดได้ **0.09–0.2 วินาที** และในเบราว์เซอร์
ตั้งแต่กดส่งจนเห็นคำตอบ **212 มิลลิวินาที**

**เกณฑ์ว่าคำถามไหนเข้าทางลัด** (`src/lib/api/sensorQuestion.js`) ต้องครบสามข้อ
1. ไม่มีคำที่แปลว่าอยากได้ความเห็น ("ควร" "ทำไม" "วิเคราะห์" "อันตราย" "เหมาะ" …)
   — "อุณหภูมิเท่าไรถึงจะอันตรายกับหมู" เป็นคำถามความรู้ ตอบด้วยเลข 26.7 °C ไม่ตรงคำถาม
2. มีคำบอกว่าถามถึงค่าไหน (อุณหภูมิ/ความชื้น/ลม/แอมโมเนีย/CO₂) หรือถามสภาพรวม
3. มีคำที่แปลว่า "ขอตัวเลข" (เท่าไร/กี่/ตอนนี้/ล่าสุด) — ยกเว้นพิมพ์สั้นมาก
   ("อุณหภูมิ" คำเดียวคือขอค่าแน่ ๆ)

ตกข้อไหนก็ส่งให้ AI ตามเดิม · **ถามค่าที่โรงเรือนนั้นไม่มีเซนเซอร์วัดก็ส่งต่อให้ AI**
(เช่นแอมโมเนีย — ฐานข้อมูลของระบบนี้มีแค่อุณหภูมิ/ความชื้น/ลม แต่ฝั่ง AI มี NH₃ ด้วย)
ห้ามตอบหัวข้อเปล่า ๆ ที่ไม่มีตัวเลข

**ทุกคำตอบต้องบอกเวลาที่วัด** ถ้าสะพานหยุดทำงาน ตัวเลขจะยังขึ้นเหมือนเดิมแต่เวลาจะค้าง
ซึ่งเป็นสิ่งเดียวที่ทำให้คนจับได้

มีปุ่ม **"ให้ AI วิเคราะห์ต่อ"** ใต้คำตอบ — ไม่ยิงไปเองอัตโนมัติ เพราะส่วนใหญ่แค่อยากรู้เลข
การรอ AI อีกเป็นนาทีคือการรบกวน

### ตอบคำถามที่ AI ย้อนถาม — พิมพ์ไม่ครบก็ต้องเข้าใจ (T1.152)

AI ย้อนถามว่าเอาจุดไหน แล้ว **รับแค่คำที่ตรงเป๊ะ** ทดสอบแล้ว:

| พิมพ์ | ผล |
| --- | --- |
| "ทั้งสอง" | ❌ ย้อนถามคำถามเดิมซ้ำ |
| "ทั้งสองจุด" | ✅ |
| "ทั้งหมด" | ✅ |
| "1" | ✅ |

คนใช้งานจริงไม่มีทางรู้ว่าต้องพิมพ์ตรงแค่ไหน แล้วจะติดวนอยู่ตรงนั้น แก้สองชั้น
(`src/lib/api/clarify.js`)

1. **แปลงตัวเลือกเป็นปุ่มให้กด** — ข้อความของมันเขียนว่า "กดเลือกได้เลย" อยู่แล้ว
   แปลว่าตั้งใจให้มีปุ่มมาแต่แรก แค่ยังไม่ได้ทำ กดปุ่มคือทางที่ไม่มีวันพิมพ์ผิด
2. **ถ้ายังพิมพ์เอง ก็แปลงคำใกล้เคียงให้ก่อนส่ง** — "ทั้งสอง" "ทั้ง 2" "สองจุด" "both"
   "อันแรก" หรือพิมพ์ชื่อจุดมาบางส่วน ("เล้า R") ก็เข้าใจหมด

**ไม่ฝังคำว่า "ดูทั้งสองจุด" ไว้ในโค้ด** — อ่านจากเครื่องหมายคำพูดในข้อความที่มันส่งมาเอง
วันหลังปลายทางเปลี่ยนคำ ก็ยังตามถูกโดยไม่ต้องแก้อะไร

**`[[ตัวเลือก]]`** บางคำตอบมันแปะปุ่มแนะนำมาท้ายด้วยเครื่องหมายนี้ (มาไม่ทุกครั้ง)
ถ้าไม่รู้จัก มันจะโผล่เป็นข้อความดิบกลางฟองคำตอบ — ตอนนี้แยกออกมาทำเป็นปุ่มแล้ว

### ความเสถียร

`/chat` ลองใหม่ได้ **ครั้งเดียว** และเฉพาะตอนต่อไม่ติดหรือฝั่งเขาตอบ 502/503/504
ปลอดภัยเพราะยังไม่มีอะไรถูกส่งออกไปหาผู้ใช้ และคำขอนี้ไม่ได้เขียนอะไร

**ไม่ลองใหม่กับ 4xx** — กุญแจผิดหรือผู้ใช้ไม่ได้ลงทะเบียน ลองกี่ครั้งก็ผิดเหมือนเดิม
ได้แค่ถ่วงเวลาให้ผู้ใช้รอเปล่า ๆ · **ไม่ลองใหม่หลังเริ่มสตรีมแล้ว** จะได้คำตอบซ้อนสองชุด

### คำตอบยาวเกินไป — สั่งจากฝั่งระบบนี้ไม่ได้ (T1.153)

**อย่าเสียเวลาลองใหม่ ลองมาแล้วสองวิธี ไม่ได้ผลทั้งคู่** (วัดความยาวเทียบจริง)

| วิธี | ผล |
| --- | --- |
| ส่ง `role: "system"` สั่งให้ตอบสั้น | **ไม่สนใจเลย** — ยาวขึ้นด้วยซ้ำ 917 → 1240 ตัวอักษร |
| ต่อท้ายคำถาม "(ตอบสั้น ไม่เกิน 5 บรรทัด)" | **คุณภาพพัง** โมเดลสับสนพิมพ์แก้ตัวเองกลางคำตอบ<br>("ขออภัย — สุนัข…ไม่ใช่ ขอใหม่") มีตัวอักษรจีนหลุดปน · ยาวเท่าเดิม 564 → 560 |
| `options.num_predict` | ไม่ใช้ — ตัดกลางประโยค ได้คำตอบค้างครึ่งทาง แย่กว่ายาวไป |

➜ **ความยาวคุมได้จาก system prompt ของเจ้าของ AI เท่านั้น** ถ้าอยากให้สั้นจริง
ต้องไปบอกคนที่ทำ AI ตัวนั้น ไม่ใช่แก้ที่นี่

**ฝั่งระบบนี้แก้ที่หน้าจอแทน** — คำตอบยาวเกิน 7 บรรทัดจะถูกพับ แล้วมีปุ่ม "อ่านคำตอบเต็ม"
(`as-clamp` + `.as-more`) วัดแล้ว 15 บรรทัด 371px → พับเหลือ 173px กางคืนได้ครบ
**ไม่ตัดข้อความทิ้ง** เป็นแค่ `overflow: hidden` ข้อความยังอยู่ครบทุกตัว
(ต่างจากการสั่ง AI ให้ตอบสั้น ซึ่งมันจะไม่พูดถึงเรื่องนั้นเลยตั้งแต่แรก)

พับเฉพาะตอนตอบจบแล้ว — ระหว่างที่ยังพิมพ์อยู่ต้องเห็นตัวอักษรไหลเข้ามา ไม่งั้นดูเหมือนค้าง

### คำถามเรื่องนอกฟาร์ม ต้องไม่ถูกคำตอบในเครื่องแย่งไป

`isOutwardQuestion` ใน `answers.js` — เจอคำว่า โรค/วัคซีน/ระบาด/ราคา/ตลาด/ข่าว/กฎหมาย
= ข้ามคำตอบในเครื่องไปเลย ค้นเว็บอย่างเดียว

**ที่ต้องมีเพราะ** คำที่ `answers.js` ใช้จับเรื่องกว้างเกินไป — เรื่อง `farms` มีคำว่า
"สุกร" กับ "หมู" ซึ่งติดแทบทุกคำถามในแดชบอร์ดหมู เจอของจริงตอน AI ล่ม:
ถาม "โรคสุกรที่ควรระวังช่วงนี้" แล้ว **ได้จำนวนฟาร์มกลับมา** และเพราะ `farms` อยู่ใน
`LOCAL_ONLY_TOPICS` มันเลยไม่ยอมค้นเว็บให้ด้วย ทั้งที่เป็นคำถามที่ค้นเว็บตอบได้ดีที่สุด

## เข้าสู่ระบบ · บัญชีผู้ใช้ · ลืมรหัสผ่าน (T1.165 · T1.201)

**หลังบ้านมีระบบยืนยันตัวตนแล้ว** — เส้นทางที่เขียนข้อมูลทุกเส้นต้องมี token
(`Authorization: Bearer …`) ส่วนเส้นทางอ่านยังเปิดไว้ เพราะหน้าเว็บต้องโหลดข้อมูล
ได้ตั้งแต่ก่อนล็อกอิน

### สร้างผู้ดูแลระบบคนแรก (ทำครั้งเดียวตอนตั้งระบบใหม่)
ตั้ง `ADMIN_PASSWORD` ใน `.env` (ยาวอย่างน้อย 8 ตัว) แล้ว
```
docker compose exec api npm run seed:admin
```
**รันซ้ำไม่เขียนทับของเดิม** — ถ้ามีผู้ดูแลระบบอยู่แล้วจะข้ามไปเฉย ๆ
(ไม่งั้นรันผิดครั้งเดียวรหัสของแอดมินตัวจริงหายทั้งระบบ)

### เปลี่ยนรหัสผ่านของตัวเอง
ตั้งค่า → บัญชี → **เปลี่ยนรหัสผ่าน** (ต้องยืนยันรหัสเดิม)
เปลี่ยนแล้ว **เครื่องอื่นที่ค้างล็อกอินไว้ถูกให้ออกจากระบบทั้งหมด** เว้นเครื่องที่กำลังใช้

⚠️ **ค่า `ADMIN_PASSWORD` ใน `.env` จะไม่ตรงกับของจริงทันทีที่เปลี่ยนรหัส**
(รหัสจริงเก็บเป็น hash ในฐานข้อมูล) — เปลี่ยนแล้วลบบรรทัดนั้นทิ้งได้เลย

### ลืมรหัสผ่าน — ทางกู้คืน
ระบบนี้ไม่มีอีเมลรีเซ็ตรหัสผ่าน และแอดมินคนเดียวที่ลืมรหัสก็ไม่มีใครตั้งให้ใหม่ได้
(หน้าจัดการผู้ใช้ต้องล็อกอินเป็นแอดมินก่อน — ไก่กับไข่) จึงมีคำสั่งกู้คืน:
```
docker compose exec -e RESET_USER=admin -e RESET_PASSWORD='รหัสใหม่ยาว ๆ' api npm run reset:password
```
- ตั้งรหัสใหม่ · **ปลดล็อกบัญชีให้ด้วย** (เผื่อโดนปิดไปแล้วไม่มีใครเปิดคืน) · ถอน session ทั้งหมด
- ส่งรหัสทาง environment variable ไม่ใช่ argument ของคำสั่ง เพราะ argument โผล่ใน `ps`
- ต้องรันจากในเครื่องที่ติดตั้งระบบ — ใครเข้า shell ได้ก็เข้าฐานข้อมูลได้อยู่แล้ว
  คำสั่งนี้จึงไม่ได้เปิดช่องอะไรใหม่

### จัดการผู้ใช้คนอื่น
ตั้งค่า → บัญชี → **จัดการผู้ใช้** (หรือ `/dashboard/users`) — ผู้ดูแลระบบเท่านั้น
เพิ่มบัญชี · เปลี่ยนสิทธิ์ · **ให้/ถอนสิทธิ์ควบคุมอุปกรณ์ (PLC)** · ตั้งรหัสใหม่ให้ · ปิดบัญชี
**ปิดบัญชีหรือตั้งรหัสใหม่ให้ = ถอน session ของคนนั้นทันที** ไม่รอหมดอายุ 30 วัน

**ระดับสิทธิ์ 4 ขั้น** (T1.251) — ขั้นสูงทำได้ทุกอย่างที่ขั้นต่ำทำได้ · ทุกระดับดูได้ทุกหน้าเท่ากัน

| ระดับ (`role`) | เพิ่มจากขั้นก่อนหน้า |
|---|---|
| ผู้ชม (`viewer`) | ดูอย่างเดียว · ตั้งค่าหน้าจอของตัวเอง |
| ผู้บันทึก (`editor`) | บันทึกในโรงเรือน · ปรับจำนวนสุกร · ภาพกล้อง · เกณฑ์และการแจ้งเตือน |
| ผู้ควบคุมอุปกรณ์ (`operator`) | สั่งพัดลม/ปั๊ม (PLC) |
| ผู้ดูแลระบบ (`admin`) | ฟาร์ม/โรงเรือน · จัดการผู้ใช้ · ค่าไฟ · ล้างข้อมูล |

- **สร้างบัญชีต้องเลือกระดับเองทุกครั้ง** ไม่มีค่าตั้งต้น · หน้าจัดการผู้ใช้มีตารางเทียบว่าแต่ละระดับทำอะไรได้
- เปลี่ยนระดับแล้ว **หน้าจอของคนนั้นเปลี่ยนตอนรีเฟรชครั้งถัดไป** · ด่านหลังบ้าน (`requireRole` ใน
  `server/src/lib/auth.js`) อ่านจากฐานทุกคำขอ มีผลทันที
- **เส้นทางสั่ง PLC จริงที่จะเพิ่มทีหลังต้องใส่ `requireRole("operator")`** (ตอนนี้การ์ดควบคุมยังเป็นข้อมูลจำลอง)
- ดูจากฐานตรง ๆ: `docker exec swine-db psql -U swine -d swinesync -c "select username, role from app_user"`

## เอาแดชบอร์ดขึ้นโฮสต์คนอื่น (เช่น lab.plotnexuslab.com)

```bash
npm run build:host     # = VITE_BASE=./ VITE_ROUTER=hash vite build
```

แล้วอัปโหลดโฟลเดอร์ `dist/` ทั้งโฟลเดอร์ (75 ไฟล์)

**ต่างจาก `npm run build` ปกติสองอย่าง — ต้องใช้คู่กันเสมอ**

| ตั้งค่า | ทำอะไร | ถ้าไม่ตั้งจะเป็นยังไง |
|---|---|---|
| `VITE_BASE=./` | ให้ไฟล์อ้างกันแบบ **พาธสัมพัทธ์** (`./assets/…`) | ตัวอัปโหลดหาไฟล์ไม่เจอแล้วปฏิเสธ ถ้าใส่พาธเต็มอย่าง `/p/mew/dashboard/` |
| `VITE_ROUTER=hash` | เก็บเส้นทางหน้าไว้หลัง `#` | ลิงก์เมนูจะชี้กลับรากโดเมน กดแล้วหลุดออกจากแอป |

**ทำไม `VITE_BASE=./` ห้ามใส่พาธเต็ม** — โฮสต์พวกนี้บอกเองว่า "เส้นทางไฟล์ไม่ต้องตั้งเอง
ระบบแก้ให้อัตโนมัติ" ตัวอัปโหลดจะอ่าน `index.html` แล้วไล่หาไฟล์ที่ถูกอ้างถึง
ถ้าใส่ `/p/mew/dashboard/assets/…` มันจะไปหาไฟล์ชื่อนั้น **ข้างในโฟลเดอร์ที่อัปขึ้นไป**
ซึ่งไม่มี แล้วขึ้นว่า "ถูกอ้างถึงในหน้าเว็บ แต่ไม่ได้อัปโหลดมาด้วย"

**ทำไมต้อง hash** — ไม่รู้ล่วงหน้าว่าโฮสต์จะวางแอปไว้โฟลเดอร์ไหน และสั่งให้เขาตั้ง
SPA fallback ให้ไม่ได้ เส้นทางที่อยู่หลัง `#` ไม่เคยถูกส่งไปถึงเซิร์ฟเวอร์
จึงกด F5 ที่หน้าลึกได้โดยไม่ต้องพึ่งอะไรจากโฮสต์เลย

**ที่อยู่ที่ได้จะหน้าตาแบบนี้**
```
https://lab.plotnexuslab.com/p/mew/dashboard/#/dashboard/environment
```

### สองข้อที่แก้ที่โค้ดไม่ได้ — ต้องรู้ก่อนเอาไปโชว์

**1. ค่าที่ผู้ใช้ตั้งไว้จะหายทุกครั้งที่ปิดหน้า** — หน้าที่อัปไปถูกรัน**แยกโดเมน**
(`pages.plotnexuslab.com`) และระบบ Cloud ฉีดสคริปต์ **แทน `localStorage` ด้วยตัวจำลอง
ในหน่วยความจำ** เจ้าของบริการเขียนไว้เองในสคริปต์นั้นว่า *"ค่าจะหายเมื่อปิดหน้า"*
เขาทำเพื่อกันไม่ให้หน้าเว็บนี้แตะรหัสผ่านของคนที่เปิด — **ไม่ใช่บั๊กของระบบนี้ และแก้ฝั่งระบบนี้ไม่ได้**
สิ่งที่หาย: เลย์เอาต์กระดาน · เกณฑ์ที่ตั้งเอง · ภาษา · token ที่ล็อกอินไว้ · บันทึกการเข้าใช้งาน

**2. ล็อกอินไม่ได้ ใช้ได้แค่สิทธิ์ผู้ใช้งาน** — แอปเรียก `/api/auth/…` ของหลังบ้าน
ที่รันอยู่ในเครื่องผู้พัฒนา บนโฮสต์นั้นไม่มี เข้าได้ทางลิงก์ "เข้าชมข้อมูลตัวอย่าง" เท่านั้น

> **แต่ค่าเซนเซอร์เป็นของจริง** — ตั้งแต่ T1.214 แอปอ่านจาก PlotNexus โดยตรง
> ไม่ได้ผ่านหลังบ้านในเครื่อง หน้าที่อัปขึ้นไปจึงเห็นอุณหภูมิ/ความชื้น/ไฟฟ้าของฟาร์ม
> กำแพงเพชรตามจริง (ส่วนฟาร์มนครสวรรค์เป็นข้อมูลตัวอย่างเหมือนเดิมทุกที่)

## ต่อหลังบ้านให้สำเนาที่วางบนโฮสต์คนอื่น (T1.221)

**ที่อยู่ของหลังบ้านไม่ได้เดาจากโดเมนอีกแล้ว** — ตั้งด้วย `VITE_API_BASE` ตอน build

| ค่า | หมายถึง | ใช้เมื่อ |
| --- | --- | --- |
| ไม่ตั้ง | `/api` ของโดเมนเดียวกัน | ปกติ — `npm run dev` และ compose (nginx ส่งต่อให้) |
| `none` | **ไม่มีหลังบ้าน** ทุกคำขอถูกปฏิเสธก่อนส่งออก | สำเนาที่วางบนโฮสต์คนอื่น (`build:host` ตั้งให้เอง) |
| URL เต็ม | หลังบ้านอยู่คนละโดเมน | หน้าเว็บอยู่โฮสต์ไฟล์นิ่ง แต่มี API สาธารณะให้ชี้กลับมา |

### ทำไมค่าตั้งต้นของ build:host ต้องเป็น `none`
เดิมทุกคำขอยิงไปที่ `/api` ของโดเมนปัจจุบัน สำเนาที่วางบน `lab.plotnexuslab.com`
จึงส่งฟอร์มเข้าสู่ระบบไปที่ `https://lab.plotnexuslab.com/api/auth/login`
= **ส่งชื่อผู้ใช้กับรหัสผ่านให้เซิร์ฟเวอร์ของคนอื่น** โดยไม่มีใครตั้งใจ
(และโดเมนนั้นมี `/api` ของตัวเองอยู่จริง ไม่ใช่ 404 เปล่า ๆ)

ตอนนี้ฟอร์มขึ้นข้อความว่าสำเนานี้ยังไม่ได้ต่อกับเซิร์ฟเวอร์ **โดยไม่ส่งอะไรออกไปเลย**
ตรวจแล้วด้วยการวางหน้าปลอมไว้ที่ `/api/auth/login` ของโฮสต์จำลอง — ไม่มีคำขอวิ่งมาถึงสักอัน

### ถ้าอยากให้เข้าสู่ระบบ/ผู้ช่วย AI ใช้ได้บนเว็บจริง ๆ

**ทาง ก. (แนะนำ) — ยกทั้งกองขึ้นเซิร์ฟเวอร์เดียว**
compose มี `web` (nginx) ที่เสิร์ฟหน้าเว็บและส่งต่อ `/api` ไป `api:3000` อยู่แล้ว
เอา `docker compose up -d` ไปรันบนเซิร์ฟเวอร์ที่มีโดเมน+HTTPS ก็จบ
**ไม่ต้องใช้ CORS เลย** เพราะหน้าเว็บกับ API อยู่โดเมนเดียวกัน และไม่ต้องตั้ง `VITE_API_BASE`
➜ ใช้ `npm run build` ธรรมดา ไม่ใช่ `build:host`

**ทาง ข. — หน้าเว็บอยู่โฮสต์ไฟล์นิ่ง API อยู่อีกที่**
1. เอา `server/` + `db` ขึ้นเซิร์ฟเวอร์ที่มีโดเมนและ **HTTPS** (ถ้าเป็น http เบราว์เซอร์จะบล็อก
   เพราะหน้าเว็บเป็น https — mixed content)
2. ฝั่ง API ตั้ง `CORS_ORIGINS=https://lab.plotnexuslab.com` (คั่นหลายโดเมนด้วยจุลภาค)
3. build ด้วย `VITE_API_BASE=https://api.โดเมนของระบบนี้/api npm run build:host`

> ⚠️ **ก่อนเปิด API ออกสู่อินเทอร์เน็ต** — ตอนนี้พอร์ต 3000/5432 ผูกกับ `127.0.0.1` โดยตั้งใจ
> การเปิดออกไปแปลว่าหน้าเข้าสู่ระบบเปิดให้ทั้งโลกลองรหัสผ่าน ควรทำสามอย่างนี้ก่อน:
> ตั้งรหัสแอดมินใหม่ให้ยาว · จำกัดจำนวนครั้งที่ลองรหัสผิด (ยังไม่มี) ·
> เลิกเก็บรหัสผ่านแบบอ่านออกได้ในตัวเลือก "จดจำบัญชี" (`lib/auth/sessions.js`)

### `CORS_ORIGINS` — กติกา
- เว้นว่าง = ไม่เปิดให้ใครเลย (ค่าตั้งต้น และถูกแล้วสำหรับทาง ก.)
- **ใส่ `*` ไม่ได้ โค้ดจะทิ้งค่านั้น** — API รับ `Authorization` เป็นกุญแจ session
  เปิดให้ทุกโดเมนเท่ากับให้เว็บไหนก็ได้ยิงคำขอแทนผู้ใช้ที่ล็อกอินอยู่
- ตรวจว่าได้ผลจริง:
  ```
  curl -i -H "Origin: https://โดเมนของระบบนี้" http://localhost:3000/api/health | grep -i access-control
  ```
  โดเมนในรายชื่อต้องเห็น `Access-Control-Allow-Origin` · โดเมนอื่นต้องไม่เห็นอะไรเลย

## เปิดแดชบอร์ดผ่าน https (จำเป็นเมื่อสาธิตจากมือถือ/เครื่องอื่น)

**ปัญหาที่ต้องรู้ก่อน** — เบราว์เซอร์ทุกตัว **ปิดไมโครโฟนและกล้องทั้งหน้า** เมื่อหน้านั้น
เปิดผ่าน `http` ที่ไม่ใช่ `localhost` เปิดจากมือถือด้วย `http://172.20.10.3:8080` เมื่อไหร่
วอยซ์กับกล้องใช้ไม่ได้ทันที และ **ไม่มีสวิตช์ไหนในเบราว์เซอร์เปิดให้ได้** (ผู้ใช้เจอเอง 17 ก.ย. 2569)

### ทำครั้งเดียว

```sh
sh ops/make-cert.sh                 # ใส่ชื่อ/ไอพีเพิ่มต่อท้ายได้
docker compose up -d --build web
```

- ใบรับรองไปอยู่ที่ `ops/certs/` — **gitignore กันไว้แล้ว ห้าม commit กุญแจส่วนตัว**
- สคริปต์ใส่ไอพีของเครื่องนี้ให้อัตโนมัติ · **เปลี่ยนเครือข่ายแล้วไอพีเปลี่ยน ให้รันใหม่**
- ไม่มีใบรับรอง = คอนเทนเนอร์ยังขึ้นปกติ แต่เสิร์ฟ http อย่างเดียว (ดูข้อความตอน `docker compose logs web`)

### ใช้งาน

| ที่อยู่ | ใช้ทำอะไร | ไมค์/กล้อง |
| --- | --- | --- |
| `http://localhost:8080` | บนเครื่องที่รัน Docker | ✅ ใช้ได้ |
| `https://<ไอพีเครื่อง>:8443` | จากมือถือ/เครื่องอื่น | ✅ ใช้ได้ (กดผ่านหน้าเตือนก่อน) |
| `http://<ไอพีเครื่อง>:8080` | จากมือถือ/เครื่องอื่น | ❌ ใช้ไม่ได้ตลอด |

**ครั้งแรกเบราว์เซอร์จะขึ้นหน้าเตือนว่าไม่ปลอดภัย** เพราะใบรับรองนี้ออกเอง ไม่มีใครรับรอง
กด Advanced → Proceed (ไอโฟน: Show details → visit this website) ครั้งเดียวจบ
หลังจากนั้นหน้านั้นนับเป็นหน้าปลอดภัยเต็มตัว ไมค์กับกล้องใช้ได้ตามปกติ

⚠️ **ใช้สำหรับสาธิตในเครือข่ายภายในเท่านั้น** ของจริงที่คนนอกเข้าถึงต้องใช้ใบรับรอง
ที่มีผู้ออกให้จริง ไม่ใช่ใบนี้ · และอย่าสอนให้ใครติดนิสัยกดผ่านหน้าเตือนใบรับรองบนเว็บอื่น

## ส่งสรุปรายวันและแจ้งเตือนเข้า LINE OA (T1.275)

**สถานะตอนนี้: โหมดซ้อม** — ระบบประกอบข้อความและบันทึกทุกอย่างเหมือนจริง แต่ไม่ยิงออกไปที่ LINE
จนกว่าจะตั้ง `LINE_DRY_RUN=0` เอง

### เปิดใช้งานทีละขั้น

1. **ออกกุญแจ** ที่ [LINE Developers Console](https://developers.line.biz/console/) → เลือก Provider → ช่องของ SWINE SYNC
   → แท็บ **Messaging API** → หัวข้อ *Channel access token (long-lived)* → กด Issue แล้วคัดลอกไว้
   ⚠️ **ไม่ใช่ Channel secret** ที่เห็นในหน้า LINE Official Account Manager — secret ใช้ตรวจลายเซ็นของ webhook ขาเข้าเท่านั้น
2. **ใส่ใน `.env`** (ไฟล์นี้ไม่ขึ้น git) แล้วสั่งขึ้นใหม่

   ```
   LINE_CHANNEL_ACCESS_TOKEN=<กุญแจที่คัดลอกมา>
   DASHBOARD_URL=https://lab.plotnexuslab.com/p/mew/dashboard/
   ```

   ```bash
   docker compose up -d api bridge
   ```

3. **ทดสอบขณะยังอยู่ในโหมดซ้อม** — ข้อความจะลง log ไม่ออกไปถึงใคร

   ```bash
   docker exec swine-api node -e "import('./src/line/notifier.js').then(async m=>{const s=await import('./src/line/summary.js');const{from,to}=s.yesterdayRange(new Date());console.log(JSON.stringify((await m.sendSummaryNow(from,to)).result));process.exit(0)})"
   docker logs --tail 5 swine-api
   ```

4. **ส่งจริง** เมื่อพอใจกับหน้าตาข้อความแล้วเท่านั้น — ตั้ง `LINE_DRY_RUN=0` ใน `.env` แล้ว `docker compose up -d api bridge`
   ส่งออกไปแล้วเรียกคืนไม่ได้ และกินโควตาของบัญชีจริง

### ตัวแปรทั้งหมด

| ตัวแปร | ค่าตั้งต้น | ความหมาย |
| --- | --- | --- |
| `LINE_CHANNEL_ACCESS_TOKEN` | ว่าง | กุญแจจาก LINE Developers Console (ห้ามขึ้นต้น `VITE_`) |
| `LINE_TARGET` | `broadcast` | `broadcast` = ทุกคนที่เป็นเพื่อนกับ OA · `push:<userId>` = ปลายทางเดียว |
| `LINE_DRY_RUN` | `1` | โหมดซ้อม · `0` = ส่งจริง |
| `LINE_NOTIFY` | `1` | `0` = ปิดตัวส่งทั้งหมด |
| `LINE_DAILY_AT` | `07:30` | เวลาส่งสรุป (เวลาไทย) สรุปของเมื่อวานเต็มวัน |
| `LINE_MAX_PER_DAY` | `20` | เพดานจำนวนครั้งต่อวัน ตาข่ายกันบัคยิงรัว |
| `LINE_ALERT_MAX_AGE_MIN` | `60` | เหตุที่เปิดค้างเกินเท่านี้ไม่ส่งย้อนหลัง |
| `DASHBOARD_URL` | ว่าง | ลิงก์ปุ่มท้ายการ์ด (ว่าง = ไม่มีปุ่ม) |

### เส้นทาง API

| เส้นทาง | สิทธิ์ | ใช้ทำอะไร |
| --- | --- | --- |
| `GET /api/line/status` | ล็อกอิน | ตั้งค่าครบไหม · โหมดซ้อมเปิดอยู่ไหม · โควตาเดือนนี้ · 10 ครั้งล่าสุด |

### ข้อจำกัดที่แก้ฝั่งระบบนี้ไม่ได้

- **ส่งไฟล์ PDF ไม่ได้** Messaging API ไม่มีชนิดข้อความแบบไฟล์ — ถ้าต้องการไฟล์จริง ต้องวางไฟล์บนเว็บ https
  สาธารณะก่อน แล้วส่งลิงก์ (ตอนนี้หลังบ้านเปิดแค่ 127.0.0.1 จึงยังทำไม่ได้)
- **โควตานับต่อผู้รับ** เพื่อน 50 คน = 50 ข้อความต่อการ broadcast หนึ่งครั้ง ดูที่เหลือใน LINE OA Manager → Monthly plan
- **ยิงไม่ออกในเครือข่ายที่ดัก TLS** — ตั้ง `NODE_EXTRA_CA_CERTS` ชี้ไปที่ใบรับรองขององค์กร (เรื่องเดียวกับ `npm install` ล้ม)

### ไล่หาสาเหตุเมื่อไม่มีข้อความเข้าไลน์

```bash
docker exec swine-db psql -U swine -d swinesync -c "select kind, ref, dry, ok, error, sent_at from line_notice order by id desc limit 10;"
```

- `dry = t` → ยังอยู่ในโหมดซ้อม
- `ok = f` พร้อม `error` → ดูข้อความที่ LINE ตอบกลับ (401 = กุญแจผิด/หมดอายุ · 429 = โควตาหมด)
- ไม่มีแถวเลย → ยังไม่มีอะไรเข้าเกณฑ์ (ไม่มีเหตุระดับวิกฤต และยังไม่ถึงเวลาสรุป) หรือ `LINE_NOTIFY=0`

**สองข้อที่ดูเหมือนพังแต่ไม่พัง** (เสียเวลาไล่มาแล้ว)

1. **`/proc/<pid>/cwd` ของ `web-server.js` ชี้ไปชุดเก่า `outputs/backend-handoff/server`**
   เพราะโปรเซสนั้น (pid เลขต่ำ ๆ) เกิดตอนกล่องบูตก่อนที่จะแก้ `autostart.sh`
   ไม่มีผลอะไรเลย — web-server อ่านหน้าเว็บจาก **`/app/dist` แบบเส้นทางตายตัว** ไม่เกี่ยวกับ cwd
   ➜ อย่าเห็นแล้วนึกว่ามี repo สองชุดแย่งกันทำงาน

2. **ไม่มี `.env` ใน `swine/app/server/`** — `autostart.sh` โหลดจาก **`$APP/.env`** คือ
   `/home/dev/swine/app/.env` ซึ่งอยู่เหนือขึ้นไปหนึ่งชั้น (`set -a; . "$APP/.env"; set +a`)
   ➜ `BRIDGE_ROLE` · `DATABASE_URL` อยู่ในไฟล์นั้น **จึงรอดการรีสตาร์ท**
   แก้บทของสะพานต้องแก้ไฟล์นี้ ไม่ใช่ `export` ตอนสั่งรัน

หลังสลับเน็ต (Wi-Fi → ฮอตสปอตมือถือ) tailscaled ไม่ได้ไปลงทะเบียนทางเข้าใหม่

แยกให้ออกว่าพังที่ชั้นไหน — ยิงเข้า **ที่อยู่สาธารณะ** เทียบกับ **ที่อยู่ในเทลเน็ต**

```bash
dig +short @1.1.1.1 <ชื่อเครื่อง>.<tailnet>.ts.net A     # ที่อยู่ที่โลกภายนอกเห็น

curl -s -o /dev/null -w "%{http_code}\n" --resolve "<ชื่อเครื่อง>.<tailnet>.ts.net:443:$(tailscale ip -4)" \
     -X POST https://<ชื่อเครื่อง>.<tailnet>.ts.net/line -d '{}'
```

- ทางในเทลเน็ตได้ **401** แต่ทางสาธารณะได้ **000** → แอปกับใบรับรองปกติ ทางเข้าของ Tailscale พัง
  แก้ด้วยการต่อใหม่ (config ของ funnel อยู่ครบ ไม่ต้องตั้งใหม่)

  ```bash
  tailscale down && tailscale up
  ```

- ได้ **401 ทั้งสองทาง** → เส้นทางถึงกันหมดแล้ว ปัญหาอยู่ที่ฝั่ง LINE (URL ที่ตั้งไว้ผิด หรือยังไม่เปิด
  "Use webhook") ดูด้วย `GET /v2/bot/channel/webhook/endpoint`

**ห้ามอ่านว่า 401 คือพัง** — 401 คือด่านลายเซ็นของระบบนี้ทำงานถูก (คำขอที่ยิงมือไม่มีลายเซ็นของ LINE)
ที่แปลว่าไม่ถึงคือ `000` กับ `COULD_NOT_CONNECT`

**ข้อจำกัดที่ต้องรู้: บอทอยู่บน Mac เครื่องนี้** เครื่องหลับเมื่อไหร่บอทเงียบทันที เรื่องเดียวกับ
ข้อมูลกลางคืนหาย (T1.263) ทางแก้ถาวรคือย้ายไปเครื่องที่เปิดตลอด แล้วเปลี่ยน Webhook URL เป็นของเครื่องนั้น

### เมนู 6 ปุ่มและการเลือกฟาร์ม (T1.277)

ทุกปุ่มตอบตามฟาร์ม/โรงเรือนที่คนนั้นเลือกไว้ (ตาราง `line_user`) ยังไม่เคยเลือก = ฟาร์มกำแพงเพชร
พิมพ์ว่า **เลือกฟาร์ม** หรือกดปุ่ม "เปลี่ยนฟาร์ม/โรงเรือน" ท้ายการ์ดใบไหนก็ได้เพื่อเปลี่ยน

ดูว่าใครเลือกอะไรไว้:

```bash
docker exec swine-db psql -U swine -d swinesync -c "select line_user_id, farm_code, barn_code, updated_at from line_user;"
```

**ฟาร์มตัวอย่างไม่มีค่าจริงในฐาน** (ตัวเลขของนครสวรรค์ถูกสร้างในเบราว์เซอร์) เลือกได้แต่ทุกเมนู
จะตอบว่าเป็นข้อมูลตัวอย่างพร้อมลิงก์ไปดูในเว็บ — **ห้ามแก้ให้แต่งตัวเลขขึ้นมาตอบ**
ถ้าวันหนึ่งย้ายฟาร์มตัวอย่างเข้าฐานจริง ให้ลบออกจาก `DEMO_FARMS` ใน `server/src/line/scope.js`

**ลิงก์ในการ์ดต้องมี `#`** เพราะเว็บที่โฮสต์ใช้ HashRouter (`npm run build:host`)
ตัวสร้างลิงก์อยู่ที่ `server/src/line/links.js` ที่เดียว เพิ่มหน้าใหม่ให้เติมใน `PAGES`

**เปลี่ยนข้อความบนปุ่มเมนูในหน้า LINE OA Manager เมื่อไหร่ ต้องมาเติมคำนั้นใน `INTENTS`**
ที่ `server/src/line/intent.js` ไม่งั้นกดปุ่มแล้วบอทจะตอบว่า "ยังตอบคำถามนี้ไม่ได้"

### ปรับว่าจะให้เตือนแค่ไหน (T1.279)

| ตัวแปร | ค่าตั้งต้น | ผล |
| --- | --- | --- |
| `LINE_ALERT_LEVELS` | `critical,serious,warning` | ระดับที่ส่งเข้าไลน์ · ตัดเหลือ `critical` ถ้าอยากเงียบสุด |
| `LINE_ALERT_COOLDOWN_HOURS` | `12` | เรื่องเดิม (โรงเรือน+รหัสเหตุ) เตือนซ้ำได้ทุกกี่ชั่วโมง |

**ระดับวิกฤตไม่เข้าช่วงพักเสมอ** — เรื่องด่วนต้องถึงมือแม้เพิ่งเตือนเรื่องเดียวกันไป

```bash
docker exec swine-db psql -U swine -d swinesync -c "select n.kind, a.level, a.code, to_char(n.sent_at at time zone 'Asia/Bangkok','DD/MM HH24:MI') as ส่งเมื่อ, n.dry from line_notice n left join alert a on a.id::text = n.ref order by n.id desc limit 10;"
```

## บันทึกงานในโรงเรือนผ่านไลน์ (T1.322)

คนหน้าฟาร์มพิมพ์ในไลน์ได้เลย ไม่ต้องเปิดเว็บ

```
หมูตาย 1        ป่วย 2         ให้อาหาร 200
ย้ายเข้า 500     ย้ายออก 50      ให้ยา 10
ยกเลิก          ← ถอนรายการที่เพิ่งบันทึก (ภายใน 30 นาที)
```

**ใช้โควตาไลน์เป็นศูนย์** เพราะเป็นการตอบกลับ (`reply`) ไม่ใช่ `push`

### ★★ ต้องผูกบัญชีก่อน ไม่งั้นบันทึกไม่ได้

บัญชีไลน์ของฟาร์มเป็น Official Account ที่**ใครก็กดเพิ่มเพื่อนได้**
ถ้าปล่อยให้ทุกคนที่พิมพ์เข้ามาบันทึกได้ คนนอกจะเขียนข้อมูลลงฐานของฟาร์มจริง
แล้วเลขนั้นไปโผล่ในหน้าฝูงสุกร รายงานส่งเวร และตัวเลขที่ผู้บริหารอ่าน

ค่าตั้งต้นคือ **อ่านได้ แต่เขียนไม่ได้** คนที่ยังไม่ถูกผูกจะได้คำตอบว่าต้องไปขอใคร

### ★ วิธีผูก — มีหน้าจอแล้ว (T1.363)

**หน้าจัดการผู้ใช้ → กล่อง "ผูกบัญชีไลน์กับผู้ใช้"** (ผู้ดูแลระบบเท่านั้น)

```
1. ให้คนนั้นทักบอทหนึ่งครั้ง           ← ระบบถึงจะรู้จักรหัสไลน์ของเขา
2. เปิดหน้าจัดการผู้ใช้ เลื่อนลงมาที่กล่องผูกบัญชี
3. แถวบนสุดคือคนที่เพิ่งทัก เลือกบัญชีผู้ใช้จากช่องเลือก
```

ช่องขวาสุดบอกทันทีว่าผูกแล้วเขียนได้หรือยัง — `บันทึกได้` · `สิทธิ์ไม่ถึงผู้บันทึก`
· `อ่านได้อย่างเดียว` (ยังไม่ผูก) · ทุกครั้งที่ผูกหรือถอนจะถูกบันทึกลงประวัติกิจกรรม

★ **ผูกกับบัญชีของคนนั้นเอง ไม่ใช่บัญชีผู้ดูแลระบบ** เพราะช่องนี้คือคำตอบของ
"ใครเป็นคนบันทึก" ซึ่งต้องตอบได้จริงเวลาตัวเลขเพี้ยนแล้วต้องไล่หาสาเหตุ

★ รหัสไลน์ที่ยังไม่เคยทักเข้ามา **ผูกไม่ได้** โดยตั้งใจ — พิมพ์ผิดตัวเดียว
แล้วได้แถวลอย ๆ ที่ไม่มีวันมีคนใช้ ซึ่งหาไม่เจอทีหลัง

### วิธีผูกด้วยมือที่ฐานข้อมูล (ทางสำรอง)

1. ให้คนนั้นทักบอทก่อนหนึ่งครั้ง เพื่อให้ระบบรู้จักรหัสไลน์ของเขา
2. ดูว่ามีรหัสไลน์ไหนเข้ามาใหม่

```bash
ssh root@<ที่อยู่ของกล่อง> 'su postgres -c "psql -d swinesync -c \"select line_user_id, farm_code, barn_code, app_user_id from line_user order by updated_at desc limit 5;\""'
```

3. ผูกรหัสไลน์นั้นกับบัญชีผู้ใช้ในระบบ (แทน `<รหัสไลน์>` และ `<ชื่อผู้ใช้>`)

```bash
ssh root@<ที่อยู่ของกล่อง> 'su postgres -c "psql -d swinesync -c \"update line_user set app_user_id = (select id from app_user where username = <ชื่อผู้ใช้>) where line_user_id = <รหัสไลน์>;\""'
```

★ **ผูกกับบัญชีของคนนั้นเอง ไม่ใช่บัญชีผู้ดูแลระบบ** เพราะช่องนี้คือคำตอบของคำถาม
"ใครเป็นคนบันทึก" ซึ่งต้องตอบได้จริงเวลาตัวเลขเพี้ยนแล้วต้องไล่หาสาเหตุ
(รายการที่มาจากไลน์ติดคำว่า `ไลน์ · <ชื่อ>` ไว้ที่ `by_name` ด้วย แยกออกจากที่บันทึกบนเว็บ)

★ **ปิดบัญชีในระบบแล้วบันทึกผ่านไลน์ไม่ได้ทันที** ไม่ต้องมาแก้ตารางนี้อีก
เพราะตัวตรวจดู `app_user.active` ด้วย

### ถอนรายการ

พิมพ์ `ยกเลิก` ถอนได้เฉพาะรายการที่**ตัวเองบันทึกผ่านไลน์** ในโรงเรือนที่กำลังดู
และต้องอยู่ในช่วง 30 นาที — การแก้ของเก่าหรือของคนอื่นต้องทำที่หน้าโรงเรือนบนเว็บ
ซึ่งเห็นรายการทั้งหมดก่อนตัดสินใจ

### ★ ถ้ารัน migrate บนกล่องแล้วขึ้นว่าลำดับไม่ตรง

เจอจริงตอนติดตั้งงานนี้ (8 ต.ค. 2569) — ฐานมีประวัติ migration ที่**ไฟล์ไม่ได้ตามขึ้นไปบนกล่อง**
เพราะรอบก่อนรันจากเครื่องผู้พัฒนา `node-pg-migrate` จึงเห็นลำดับขาดแล้วปฏิเสธ

แก้ด้วยการส่งไฟล์ที่ขาดขึ้นไปให้ครบก่อน (ของที่รันแล้วจะถูกข้ามเอง) ตรวจว่าตรงกันด้วย

```bash
ssh root@<ที่อยู่ของกล่อง> 'diff <(ls /home/dev/swine/app/server/src/db/migrations/ | sed "s/\.js$//" | sort) <(su postgres -c "psql -d swinesync -At -c \"select name from pgmigrations order by name;\"" | sort)'
```

บรรทัดที่มี `<` คือไฟล์ที่ยังไม่ได้รัน · บรรทัดที่มี `>` คือ**ที่รันแล้วแต่ไฟล์หาย** ซึ่งต้องเติม

## นโยบายอายุข้อมูล — ตรวจและแก้ที่ไหน (12 ต.ค. 2569)

### สรุปสั้น
นโยบายบีบอัด/ลบข้อมูลของ TimescaleDB **อยู่ในฐานข้อมูล ไม่ใช่ในไฟล์**
`add_retention_policy` ถูกเรียกครั้งเดียวตอน migrate แล้วค่าฝังอยู่ใน job ตั้งแต่นั้น
**แก้ `RAW_RETENTION_DAYS` ใน `.env` แล้วรีสตาร์ตไม่มีผลอะไรเลย** — ของที่รันอยู่ไม่อ่านตัวแปรนั้น
ต้องเขียน migration ที่ `remove_retention_policy` แล้ว `add_` ใหม่

### ★ รัน migrate บนกล่อง — สองจุดที่พลาดง่าย

```bash
ssh root@<ที่อยู่ของกล่อง> 'cd /home/dev/swine/app/server && set -a && . ../.env && set +a && npm run migrate up'
```

**ต้องมี `up`** — `npm run migrate` เฉย ๆ จะพ่น**หน้าช่วยเหลือ**แล้วจบด้วย exit 0
ดูเหมือนสำเร็จทั้งที่ไม่ได้รันอะไรเลย · ไม่มีคำว่า error ให้เห็นสักคำ

**ต้องโหลด `.env` เข้า shell เอง** — `--envPath ../.env` ใน script ไม่พอเมื่อรันบนกล่อง
จะขึ้น `The DATABASE_URL environment variable is not set`

★ **อย่าเชื่อ exit code** — ยืนยันผลที่ `timescaledb_information.jobs` ทุกครั้ง (คำสั่งข้างล่าง)

### ดูว่าตอนนี้ตั้งอะไรไว้

```bash
ssh root@<ที่อยู่ของกล่อง> 'su postgres -c "psql -d swinesync -At -F\"|\" -c \"select job_id, application_name, schedule_interval, config::text, next_start from timescaledb_information.jobs order by job_id;\""'
```

อ่าน `config` เป็นหลัก — `drop_after` คืออายุค่าดิบ · `compress_after` คือเมื่อไหร่บีบอัด

### ดูว่างานเบื้องหลังรันจริงไหม

```bash
ssh root@<ที่อยู่ของกล่อง> 'su postgres -c "psql -d swinesync -At -F\"|\" -c \"select job_id, last_run_status, last_successful_finish, total_runs, total_failures from timescaledb_information.job_stats order by job_id;\""'
```

`total_failures` ไม่ศูนย์ไม่ได้แปลว่าพังอยู่ — ดู `last_run_status` ด้วย
ช่วงกล่องดับงานพวกนี้พลาดเป็นปกติแล้วกลับมาเองเมื่อกล่องขึ้น

### ★ ข้อมูลหายเมื่อไหร่ ดูที่ "ก้อน" ไม่ใช่ที่แถว

Timescale ลบทีละ chunk และลบเฉพาะ chunk ที่**ปลายก้อน**เลยกำหนดไปแล้ว
แปลว่าค่าที่เก่ากว่ากำหนดจะอยู่ต่อได้อีกจนครบความยาวก้อนหนึ่ง (ตั้งต้น 7 วัน)
ถ้าอยากรู้ว่าก้อนไหนจะหายก่อน ให้ดูคอลัมน์ `range_end`

```bash
ssh root@<ที่อยู่ของกล่อง> 'su postgres -c "psql -d swinesync -At -F\"|\" -c \"select chunk_name, range_start::date, range_end::date, is_compressed from timescaledb_information.chunks where hypertable_name = '"'"'sensor_reading'"'"' order by range_start limit 5;\""'
```

### ขนาดจริงเทียบดิสก์

```bash
ssh root@<ที่อยู่ของกล่อง> 'df -h /; su postgres -c "psql -d swinesync -At -F\"|\" -c \"select hypertable_name, pg_size_pretty(total_bytes) from timescaledb_information.hypertables h, lateral hypertable_detailed_size(format('"'"'%I.%I'"'"', hypertable_schema, hypertable_name));\""'
```

วัดเมื่อ 12 ต.ค. 2569: `sensor_reading` 14 MB (484k แถว บีบอัดแล้ว) ·
`power_reading` 18 MB (97k แถว ยังไม่บีบ) · ดิสก์เหลือ 1.4 TB จาก 1.8 TB

★ **ค่าดิบสามเดือนกินแค่ 14 MB** — ถ้าคิดจะลบข้อมูลเพื่อประหยัดที่ ให้วัดก่อนทุกครั้ง
ตัวเลขจริงมักเล็กกว่าที่คิดหลายเท่า และต้นทางไม่เก็บย้อนหลังให้ ลบแล้วดึงกลับไม่ได้

## ★ กล่องยิงไปหาเครื่องใน Tailscale ไม่ได้ — สะพาน `tailscale nc` (30 ต.ค. 2569)

### อาการที่หลอกคน

`tailscale status` บนกล่องเห็นเครื่องปลายทางครบ `tailscale ping` ตอบ `pong` ปกติ
แต่ `curl` / `fetch` ไปหาเครื่องนั้น **ได้ `000` ไปไม่ถึง** ทุกครั้ง

```
tailscale ping <ที่อยู่ของเครื่องกล้อง AI>   pong 73ms        ← ผ่าน
curl http://<ที่อยู่ของเครื่องกล้อง AI>:8080 000              ← ไม่ผ่าน
curl ไปหาเครื่องผู้พัฒนา      000              ★ ตัวตัดสิน
```

**ตัวตัดสินคือยิงไปหาเครื่องที่รู้ว่าใช้งานได้อยู่** ถ้าเครื่องนั้นก็ไปไม่ถึง
แปลว่าปัญหาอยู่ที่กล่อง ไม่ใช่ที่ปลายทาง — อย่าเพิ่งไปโทษฝั่งโน้น

### สาเหตุ

กล่องรันในคอนเทนเนอร์ที่ **ไม่มี `/dev/net/tun`** `tailscaled` จึงต้องรันโหมด
`--tun=userspace-networking` ซึ่งจัดการการเชื่อมต่อในตัวเอง
**ไม่สร้างการ์ดเน็ตเวิร์กเสมือนและไม่ลงเส้นทางของช่วง `100.x` ในระบบ**
โปรแกรมทั่วไปจึงหาทางออกไม่เจอ ส่วน `tailscale ping` วิ่งผ่าน `tailscaled` เองจึงผ่าน

★ `ip route get 100.x.x.x` **ใช้วินิจฉัยเรื่องนี้ไม่ได้** มันจะตอบว่ามีเส้นทางออก `eth0`
เหมือนกันทั้งเครื่องที่ติดต่อได้และติดต่อไม่ได้ เพราะมันเจอ default route
ใครเอาผลนี้ไปอ่านจะสรุปว่า "เส้นทางปกติ" แล้วไปหาผิดที่

### ★★ ห้ามแก้ด้วยการรีสตาร์ต `tailscaled`

ใส่แฟล็ก `--socks5-server=` หรือ `--outbound-http-proxy-listen=` แล้วรีสตาร์ตก็แก้ได้
**แต่ห้ามทำ** เพราะ **Tailscale SSH คือทางเดียวที่เข้ากล่องได้** ถ้ามันไม่กลับขึ้นมา
คือเข้ากล่องไม่ได้อีกเลย — โดเมนเสิร์ฟแค่เว็บไม่ใช่เชลล์ และไม่มีแผงเปิด-ปิดเครื่อง

### ★ "ตอบ 200" ไม่ได้แปลว่า AI ทำงาน

ทีมกล้องบอกเองว่า `/api/health` ของเขาตรวจแค่ว่าเซิร์ฟเวอร์ตอบ
เครื่องที่ค้างกลางทางก็ยังตอบ 200 เหมือนเดิมทุกประการ `/api/vision/health` จึงตัดสินจาก
`fps` คู่กับเวลาของผลประมวลผลล่าสุด แล้วตอบเป็นสี่สถานะ (`server/src/vision/health.js`)

| สถานะ | แปลว่า |
| --- | --- |
| `working` | fps เดินอยู่ และมีผลประมวลผลใหม่ใน 10 นาที |
| `idle` | fps เดินอยู่ แต่ยังไม่พบสุกรในภาพช่วงที่ผ่านมา — **ไม่ใช่พัง** |
| `down` | ต่อไม่ได้ หรือตอบ 200 แต่ `fps` เป็นศูนย์ |
| `unknown` | อ่านประวัติจากคลังข้อมูลไม่ได้ — ไม่เดาว่าทำงานอยู่ |

★ `idle` ต้องไม่ขึ้นเป็นสีแดง ถ้าไม่มีสุกรเดินผ่านกล้องจะไม่มีผลประมวลผลเขียนลงฐานเลย
ซึ่งถูกต้องแล้ว — ตีว่าเงียบ = พัง หน้าจอจะแดงทั้งคืนทุกคืนจนคนเลิกเชื่อป้ายสถานะ

★ **ต่อปลายทางไม่ได้ตอบ 503 (`vision_unreachable`) ไม่ใช่ตอบค่าเก่าหรือค่าจำลอง**
ยกเว้น `/health` ที่ตอบ 200 เสมอ เพราะ "ล่ม" คือคำตอบที่หน้าจอต้องใช้

### ⚠ `/weights` ของเขาไม่รับ `?limit=` — มันคืน **100 แถวล่าสุด** ตายตัว

ส่ง `?limit=2` ไปได้ขนาดตอบเท่าเดิมเป๊ะ (17,698 ไบต์ ทั้งสองครั้ง — ตรวจ 30 ต.ค. 2569)
นับแถวแล้วได้ **100 พอดี** ทุกครั้ง แปลว่าเพดานอยู่ที่ 100 ไม่ใช่คืนทั้งตาราง
ขนาดจึงไม่โตตามอายุการใช้งาน แต่ **ขอช่วงเวลาที่ต้องการไม่ได้** และ
เคยเห็นของจริงช้าจนหมดเวลา (ปกติ 0.8 วิ บางจังหวะเกิน 8 วิ)

`/health` จึง**เก็บอายุผลประมวลผลไว้ใช้ซ้ำ 30 วินาที** ไม่ไปถามทุกครั้งที่หน้าจอถาม
ถ้าวันหนึ่งทีมกล้องใส่ `?limit=` หรือช่วงเวลาให้ ให้เปลี่ยนมาใช้แทน

★ ผลข้างเคียงที่ต้องรู้: **ดูประวัติย้อนหลังเกิน 100 รายการล่าสุดไม่ได้**
ตอนตรวจ 100 แถวครอบคลุมแค่ 72 นาที หน้าประวัติน้ำหนักจึงทำได้แค่ช่วงสั้น ๆ
จนกว่าจะขอให้เขาเปิดช่วงเวลาให้

### ก. พื้นที่ดิสก์บนเครื่องผู้พัฒนาลดทุกวันทั้งที่ไม่มีใครสร้างไฟล์ — วัด 19 ต.ค. 2569

ไล่หาสาเหตุที่พื้นที่หายวันละ ~1.5 GiB แล้วพบว่า **ไม่ใช่ไฟล์ของใครเลย — เป็น swap**

```
vm.swapusage:  total = 16 GB   used = 15.7 GB   (เหลือ 677 MB)
แรมทั้งเครื่อง: 8 GB          Pageouts: 18,226,213 ครั้ง
วอลุ่ม VM (swap + sleepimage) กินไป 17.2 GB
```

เครื่องนี้แรม 8 GB แต่รัน Docker 8 คอนเทนเนอร์ + แอปตัวโต ๆ พร้อมกัน
macOS จึงขยาย swap ทีละ 1 GB เรื่อย ๆ และ **ไม่คืนพื้นที่จนกว่าจะรีสตาร์ต**

**หลักฐานที่ตัดความเป็นไปได้อื่นทิ้ง** — ไล่ไฟล์ที่ถูกเขียนใน 24 ชม. ทั้งโฟลเดอร์บ้าน
ได้ 13.28 GiB แต่ 12.39 GiB ในนั้นคือ `Docker.raw` ที่มีอยู่ก่อนแล้ว **ของใหม่จริงไม่ถึง 1 GB**
➜ นี่คือเหตุผลที่ลบแคชแล้วกลับมาตันอีกทุกครั้ง ไม่ว่าจะลบกี่รอบ

| ทำอะไรได้ | ได้คืนเท่าไร |
| --- | --- |
| **รีสตาร์ตเครื่อง** | ~15 GB ทันที · ปลอดภัยและเร็วที่สุด · ยังไม่ได้ทำ ณ 30 ต.ค. 2569 |
| ปิด `wx-lab` (JupyterLab ที่เปิดค้างไว้) | คืนแรม 112 MB · เปิดกลับด้วย `docker compose start wx-lab` |
| ~~ลบ `~/Library/Application Support/Claude/vm_bundles`~~ | ทำแล้ว 19 ต.ค. 2569 — ได้คืน 11 GB (ว่าง 6.0 → 17 GiB) |

### ข. ของเก่าที่ยังค้างในประวัติบน GitHub + วิธีย้ายรีโปที่ไม่ลากไปด้วย

โค้ดขึ้น GitHub แบบ **private** ที่ `<บัญชีส่วนตัวของผู้พัฒนาเดิม>/cpf_dashboard` เมื่อ 19 ต.ค. 2569
วันเดียวกันล้างประวัติด้วย `git filter-branch` เอาสองโฟลเดอร์ออก
(`weather/backup/` 93 MB · `exports/` 14 MB) แล้ว force push ทับ — `.git` ลดจาก 180 → 34 MB

**แต่ force push ย้ายแค่ปลาย branch** คอมมิตชุดเก่ากลายเป็น dangling ซึ่ง GitHub
ยังเสิร์ฟให้ถ้ารู้ SHA (ตรวจ 19 ต.ค.: เรียก `a99094e` ยังได้) ของที่ยังดึงได้ทางนั้นคือ
ไฟล์ CSV 93 MB กับ **กุญแจ PlotNexus** ที่ฝังใน `exports/plotnexus-dashboard.html`
(ฝังเพราะชื่อขึ้นต้นด้วย `VITE_` จึง build ลงไฟล์)

เสี่ยงต่ำ: รีโปเป็น private · กุญแจถูกถอนสิทธิ์ตั้งแต่ 11 ก.ย. 2569 · ตอนล้างยังไม่มีใคร clone

⚠ **ต้องจัดการให้จบก่อนทำสองอย่างนี้**
- **เปลี่ยนรีโปเป็น public** — ของเก่าจะเข้าถึงได้จากภายนอกทันที
- **ขอกุญแจ PlotNexus คืน** — ห้ามใช้ตัวเดิม ต้องขอใบใหม่เสมอ ตัวเดิมถือว่าหลุดแล้ว

ตรวจ 28 ต.ค. 2569: **ทุก blob ที่เข้าถึงได้ 1,914 ก้อน** + เอกสาร Office 23 เวอร์ชัน
**ไม่มีค่าความลับจริงเลย** (ที่เจอคือ `process.env.…`, `sha512-…` ใน lock file, GUID ของ Word)
แปลว่าของที่ค้างเป็นของฝั่ง GitHub เท่านั้น **ไม่ได้อยู่ในประวัติที่ push ขึ้นไป**

| วิธีย้ายรีโป | คอมมิต dangling |
| --- | --- |
| Transfer ownership | **ตามไปด้วย** — ย้ายตัวรีโปเดิมทั้งก้อน |
| สร้างรีโปเปล่าใน org แล้ว push | **ไม่ตามไป** — push ส่งแต่ออบเจกต์ที่เข้าถึงได้ |

➜ ใช้วิธีที่สองแล้วลบรีโปเก่า ได้ทั้งย้ายเจ้าของและปิดเรื่องของเก่าในครั้งเดียว
ตรวจแล้วว่าไม่มี issue / PR / fork / star และ **การ deploy ไม่กระทบ** เพราะบนกล่องไม่ใช่ git repo
⚠ ต้องเป็น **organization ของบริษัท** ไม่ใช่บัญชีส่วนตัวของใครอีกคน
⚠ `weather/backup/obs-csv-source-backup.csv` 93 MB **ห้าม push ขึ้นรีโปใหม่** — `.gitignore` ครอบไว้แล้ว
แต่ถ้าคัดลอกโฟลเดอร์ไปที่อื่นต้องพา `.gitignore` ไปด้วย
