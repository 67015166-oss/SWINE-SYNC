# 3 · คู่มือ GitHub สำหรับผู้เริ่มต้น

[← กลับสารบัญ](README.md)

> คู่มือนี้เขียนแยกเป็นเล่มของตัวเอง สำหรับคนที่**ไม่เคยใช้ Git มาก่อนเลย**
> ทุกคำสั่งในหน้านี้คือคำสั่งที่ใช้จริงกับโปรเจกต์นี้ ไม่ใช่ตัวอย่างสมมติ

## 3.1 GitHub คืออะไร และใช้ทำอะไรในโครงการนี้

**Git** คือโปรแกรมที่จำว่าไฟล์เปลี่ยนไปอย่างไรบ้างในแต่ละครั้งที่บันทึก
**GitHub** คือเว็บที่เก็บประวัตินั้นไว้บนอินเทอร์เน็ต ให้หลายคนทำงานไฟล์เดียวกันได้

ในโครงการนี้ใช้เพื่อสามอย่าง

1. **เก็บโค้ดไว้นอกเครื่อง** — เครื่องพังแล้วงานไม่หาย
2. **ย้อนกลับได้** — แก้แล้วพังเมื่อไร ย้อนไปจุดที่ยังดีอยู่ได้
3. **ส่งมอบ** — คนที่มารับช่วงต่อดึงโค้ดทั้งหมดไปได้ด้วยคำสั่งเดียว

**ที่อยู่ของโปรเจกต์นี้**

```
<ที่อยู่รีโปของบริษัท>
```

★ เป็น repository แบบ **private** — ต้องถูกเชิญก่อนถึงจะเห็น

## 3.2 สมัครและเข้าสู่ระบบ GitHub

1. เปิด `https://github.com` กด **Sign up**
2. กรอกอีเมล · ตั้งรหัสผ่าน · ตั้งชื่อผู้ใช้ (username)
3. ยืนยันอีเมลจากลิงก์ที่ GitHub ส่งไปให้
4. ส่งชื่อผู้ใช้ให้ผู้ดูแล repository เพื่อขอเชิญเข้าโปรเจกต์
5. กดรับคำเชิญจากอีเมล หรือที่ `<ที่อยู่รีโปของบริษัท>/invitations`

## 3.3 ติดตั้ง Git

| ระบบ | วิธีติดตั้ง |
| --- | --- |
| macOS | พิมพ์ `git --version` ในเทอร์มินัล ถ้ายังไม่มี เครื่องจะชวนติดตั้งให้เอง |
| Windows | ดาวน์โหลดจาก `https://git-scm.com/download/win` แล้วกด Next จนจบ |
| Linux | `sudo apt install git` |

ตั้งชื่อและอีเมลของตัวเองครั้งเดียว — ชื่อนี้จะติดไปกับทุกครั้งที่บันทึกงาน

```bash
git config --global user.name "ชื่อของคุณ"
```

```bash
git config --global user.email "อีเมลที่สมัคร GitHub"
```

## 3.4 ดาวน์โหลดโค้ดครั้งแรก (Clone)

**Clone** = ดึงทั้งโปรเจกต์พร้อมประวัติทั้งหมดลงมาที่เครื่อง ทำครั้งเดียวพอ

```bash
git clone <ที่อยู่รีโปของบริษัท>.git
```

GitHub จะถามชื่อผู้ใช้กับรหัส — ★ **ช่องรหัสผ่านต้องใส่ Personal Access Token ไม่ใช่รหัสผ่านปกติ**
สร้างได้ที่ Settings → Developer settings → Personal access tokens → Generate new token
เลือกสิทธิ์ `repo` แล้วคัดลอกเก็บไว้ (GitHub จะแสดงให้ดูครั้งเดียว)

> ถ้าไม่อยากพิมพ์โทเคนทุกครั้ง ใช้ GitHub Desktop หรือ `gh auth login` แทนได้

## 3.5 ดึงโค้ดเวอร์ชันล่าสุด (Pull)

**ทำทุกครั้งก่อนเริ่มแก้งาน** — ไม่งั้นจะแก้ทับของคนอื่น

```bash
git pull origin main
```

## 3.6 ดูว่าตัวเองแก้อะไรไปบ้าง

```bash
git status
```

```bash
git diff
```

## 3.7 บันทึกและส่งขึ้น GitHub (Commit · Push)

สามขั้นเสมอ — เลือกไฟล์ → บันทึก → ส่งขึ้น

```bash
git add .
```

```bash
git commit -m "แก้หน้าแจ้งเตือนให้แสดงชื่อโรงเรือน"
```

```bash
git push origin main
```

★ **ข้อความ commit เขียนเป็นภาษาไทยได้** และควรบอกว่า*ทำอะไร* ไม่ใช่ว่า*แก้ไฟล์ไหน*
โปรเจกต์นี้ใช้รูปแบบ `หัวข้อสั้น (รหัสงาน)` เช่น `แก้บั๊กช่องติ๊กส่งกิจกรรมเข้าไลน์ (T1.367)`

## 3.8 สร้าง Branch และ Merge

**Branch** = เส้นทางแยกไว้ลองของ โดยไม่กระทบเส้นหลัก (`main`)
ใช้เมื่อแก้อะไรที่ใหญ่หรือเสี่ยง

```bash
git switch -c แก้หน้าแจ้งเตือน
```

ทำงาน แล้ว commit ตามปกติ จากนั้นส่งขึ้น

```bash
git push -u origin แก้หน้าแจ้งเตือน
```

รวมกลับเข้าเส้นหลัก

```bash
git switch main && git pull origin main && git merge แก้หน้าแจ้งเตือน
```

ลบ branch ที่รวมแล้ว

```bash
git branch -d แก้หน้าแจ้งเตือน
```

## 3.9 แก้ปัญหาเบื้องต้น

| อาการ | สาเหตุ | ทางแก้ |
| --- | --- | --- |
| `Authentication failed` | ใส่รหัสผ่านแทนโทเคน | สร้าง Personal Access Token แล้วใช้แทนรหัสผ่าน |
| `Updates were rejected` | มีคนอื่น push ก่อน | `git pull origin main` แล้ว push ใหม่ |
| `CONFLICT (content): Merge conflict in ...` | สองคนแก้บรรทัดเดียวกัน | ดูข้อ 3.10 |
| `fatal: not a git repository` | อยู่ผิดโฟลเดอร์ | `cd cpf_dashboard` ก่อน |
| เผลอ commit ไฟล์ `.env` | ไฟล์ความลับหลุด | **หยุดทันที อย่า push** แล้วแจ้งผู้ดูแลระบบ |
| อยากทิ้งที่แก้ไปทั้งหมด | — | `git restore .` (★ กู้คืนไม่ได้) |

## 3.10 เมื่อเจอ Merge Conflict

Git จะใส่เครื่องหมายไว้ในไฟล์แบบนี้

```
<<<<<<< HEAD
บรรทัดที่แก้ไว้ในเครื่องนี้
=======
บรรทัดที่คนอื่นเขียน
>>>>>>> main
```

ทำสามขั้น

1. เปิดไฟล์ ลบเครื่องหมาย `<<<<<<<` `=======` `>>>>>>>` ออก แล้วเหลือไว้เฉพาะเนื้อหาที่ถูกต้อง
   (อาจเป็นฝั่งนี้ ฝั่งนั้น หรือรวมกันทั้งคู่ — **ต้องคิด ไม่ใช่เลือกมั่ว**)
2. `git add <ชื่อไฟล์>`
3. `git commit`

★ **ถ้าไม่แน่ใจว่าควรเหลืออันไหน ให้ถามคนที่เขียนอีกฝั่งก่อน** การเดาแล้วลบโค้ดคนอื่นทิ้ง
เป็นวิธีที่ทำให้บั๊กโผล่ทีหลังโดยไม่มีใครรู้ว่ามาจากไหน

## 3.11 แนวทางทำงานหลายคนโดยโค้ดไม่ทับกัน

1. **`git pull` ก่อนเริ่มงานทุกครั้ง** — ข้อนี้ข้อเดียวกันปัญหาได้เกินครึ่ง
2. **commit บ่อย ๆ ทีละเรื่อง** ดีกว่า commit ใหญ่ครั้งเดียวตอนจบวัน
3. **ตกลงกันว่าใครแก้ไฟล์ไหน** ก่อนลงมือ
4. **งานใหญ่หรืองานเสี่ยง ให้แยก branch** แล้วค่อยรวม
5. **`npm run build` และ `npm test` ต้องผ่านก่อน push เสมอ** — push โค้ดที่พังขึ้นไป คนอื่นที่ pull ต่อจะพังตาม
6. **ห้าม push ไฟล์ `.env` หรือไฟล์ความลับใด ๆ** — มี `.gitignore` กันไว้แล้ว อย่าแก้ให้มันผ่าน

## 3.12 คำสั่งที่ใช้บ่อยที่สุด สรุปไว้ที่เดียว

| อยากทำอะไร | คำสั่ง |
| --- | --- |
| ดึงโค้ดล่าสุด | `git pull origin main` |
| ดูว่าแก้อะไรไปบ้าง | `git status` |
| บันทึกงาน | `git add .` แล้ว `git commit -m "..."` |
| ส่งขึ้น GitHub | `git push origin main` |
| ดูประวัติย้อนหลัง | `git log --oneline -10` |
| สร้างเส้นทางแยก | `git switch -c ชื่อ-branch` |
| กลับเส้นหลัก | `git switch main` |
| ทิ้งที่แก้ทั้งหมด | `git restore .` |
